## الملخص التنفيذي

Jomla.ma مشروع **مكتمل هندسياً بشكل لافت للانتباه** بالنسبة لمرحلته. البنية التقنية سليمة، الأمان مدروس، ورحلة المورد والمشتري مُختبرتان ومثبتتان محلياً. المشروع **جاهز للانتقال إلى الاستضافة** بعد اتخاذ قرارات تشغيلية، وليس بعد إعادة بناء.

**المشكلة الأولى والأخطر:** الجهاز البصري للمنصة — التصميم وتجربة المستخدم — **لا يعكس طموح المنصة ولا يناسب تاجراً مغربياً غير تقني**. الواجهة الحالية هي نموذج أولي وظيفي، لكنها ليست منتجاً جاهزاً لعرضه على موردين حقيقيين.

**المشكلة الثانية:** الذكاء الاصطناعي موجود في الكود **بشكل آمن ومدروس** لكنه معطل فعلياً (401 من Claude). البحث البصري يعمل كنظام بصمة بيكسل محلي مع حدود صريحة موثقة — وهذا **صادق وأمين** لكنه بعيد عن الرؤية الاستراتيجية.

**القرار الهندسي:** لا داعي لإعادة البناء. ما يلزم هو: (1) إعادة تصميم الواجهة بهوية مغربية احترافية، (2) إصلاح مفتاح AI، (3) النشر الآمن.

## 2. تقييم التصميم وتجربة المستخدم (UX/UI)

### 2.1 الحكم العام

> **الواجهة الحالية هي نموذج أولي وظيفي مكتوب بأسلوب "developer-first"، لا منتجاً موجهاً لتاجر مغربي غير تقني.**

الحكم مستند إلى: قراءة الكود (index.css: 67 سطراً — App.js: 258 سطراً — جميع الصفحات في ملف واحد).

### 2.2 تقييم كل شاشة رئيسية

#### الصفحة الرئيسية والبحث (App.js)

| المعيار | التقييم | الدليل من الكود |
|---|---|---|
| جودة التصميم | ضعيف | `.hero` gradient بدون صورة أو هوية بصرية |
| تسلسل منطقي | متوسط | شريط بحث + فلاتر + شبكة منتجات — مقبول |
| الهاتف | مقبول | `@media(max-width:600px)` موجود لكن محدود |
| العربية RTL | ناقص | لا `dir="rtl"` صريح على `<html>` — يعتمد على المتصفح |
| خاصية التنقل | خطير | SPA بدون URL routing — لا يمكن الرجوع بزر المتصفح |
| حالات الفشل | جيد | `<Notice error>` موجود وواضح |
| مناسب لغير التقنيين | ضعيف | زر "الإشراف" في رأس الصفحة مرئي لجميع المستخدمين |

**مشكلة حرجة:** الزر `<button onClick={() => setPage('admin')}>{t('admin_btn')}</button>` مرئي لأي زائر. هذا خلل UX (وأمان) — حتى لو الواجهة تطلب بيانات اعتماد، ظهور "الإشراف" في رأس الصفحة العامة غير احترافي.

#### صفحة التسجيل (RegisterPage.jsx)

| المعيار | التقييم |
|---|---|
| بساطة | جيد — نموذج واحد بـ 6 حقول |
| وضوح الحقول | مقبول |
| التحقق من المدخلات | ضعيف — لا تحقق في الواجهة قبل الإرسال |
| مناسب للتاجر | متوسط — حقل "نوع الحساب" يعرض "موظف مورد (يتطلب دعوة)" وهو مربك |
| بدون تفسير الـ ICE/RC | غائب تماماً |

**فجوة مهمة:** لا يوجد شرح لماذا تطلب المنصة الـ ICE أو RC، ولا توجد خطوة "تحقق من البريد الإلكتروني". في السياق المغربي، كثير من التجار سيتوقف عند هذه النقطة.

#### لوحة تحكم المورد (SupplierDashboard.jsx — 293 سطراً)

| المعيار | التقييم |
|---|---|
| التنقل بين الأقسام | تبويب (tab) بسيط — مقبول |
| الوضوح | متوسط — كمية كبيرة من state و data في ملف واحد |
| الهاتف | مقبول تقنياً |
| التبعية بين الشاشات | لا يوجد breadcrumb — صعب التوجه |
| الإشعارات | موجودة لكن مدمجة — لا badge عدد الإشعارات في الأيقونة |

**ملاحظة هندسية:** `SupplierDashboard.jsx` يتعامل مع: الملف الشخصي، المنظمة، المتاجر، المنتجات، RFQ، التوريد، التقييمات، الإشعارات، التحليلات، التحقق، الرسائل، العروض — **كل هذا في ملف واحد بـ 293 سطراً**. هذا ثقل تقني سيصبح مشكلة عند التوسع.

#### محرر المنتج (ProductEditor.jsx — 204 سطراً)

**الأفضل في الواجهة.** تصميم محكم، إقرار صريح للحقوق، منع النشر بدون اعتماد، شرائح أسعار. لكن:

| المشكلة | التفاصيل |
|---|---|
| لا معاينة للمنتج قبل النشر | المورد لا يرى كيف سيظهر منتجه |
| المصطلحات التقنية | "MOQ" و"pricingMode" و"on_request" قد تكون مربكة |
| ترتيب الحقول | الصورة في النهاية — يجب أن تكون في البداية |
| لا خطوات مرئية | المورد لا يعرف في أي خطوة هو من أصل كم |

#### بطاقة المنتج (ProductCard.jsx)

| المعيار | التقييم |
|---|---|
| المعلومات الأساسية | جيد — السعر، MOQ، التوفر، الفئة |
| حجم الصورة | `height: 185px` ثابت — قد تنقطع بعض الصور |
| زر RFQ | معطل عند `!available` — منطقي لكن يفقد فرص الاتصال |
| تمييز المطابقة | `matchBasis`, `matchType` — وظيفي لكن العبارات تقنية |
| غياب صفحة المنتج المستقلة | النقر على المنتج يفتح RFQ مباشرة — لا صفحة تفاصيل |

**فجوة حرجة:** لا توجد صفحة منتج مستقلة (Product Detail Page). المستخدم لا يمكنه قراءة وصف كامل، رؤية صور متعددة، أو مشاركة رابط منتج محدد.

#### لوحة المشتري (BuyerDashboard.jsx)

| المعيار | التقييم |
|---|---|
| الوضوح | مقبول — تبويب بين RFQs، Sourcing، Notifications |
| واجهة المفاوضة | وظيفية لكن جافة — لا timeline للرحلة |
| الهاتف | inline styles بدلاً من CSS classes — صعب الصيانة |
| فهم حالات الطلب | pending → responded → accepted — نصوص واضحة |
| حساب الإجمالي | مُعروض (سعر × كمية) — جيد |

### 2.3 ما يستحق الإشادة في التصميم

- نظام الألوان متسق (`--brand`, `--teal`, `--ink`)
- استخدام CSS variables — قابل للتعديل لاحقاً
- حالات التحميل والفشل مُعالَجة في كل المكونات
- `Notice` component ثنائي (عادي/خطأ) — بسيط وفعال
- `WorkspaceHeader` موحد عبر كل الشاشات

### 2.4 مشاكل UX الحرجة المستقلة عن الرأي الشخصي

1. **لا URL routing** — لا يمكن مشاركة رابط منتج أو متجر. لا يمكن الرجوع بزر المتصفح.
2. **زر "الإشراف" عام** — ظاهر لجميع المستخدمين في رأس الصفحة.
3. **لا صفحة منتج مستقلة** — لا وصف كامل، لا صور متعددة.
4. **شاشة المتاجر متواضعة** — قائمة بسيطة بدون صورة أو تفاصيل أو بحث.
5. **لا feedback للمورد بعد الاعتماد** — المتجر يُعتمد لكن لا يوجد بريد/إشعار واضح.
6. **اتجاه RTL غير مُصرَّح** — `dir="rtl"` لا يُضاف صريحاً على `<html>`.

## 4. تقييم الذكاء الاصطناعي والبحث البصري

### 4.1 ما هو موجود فعلاً — قراءة مستقلة للكود

**البحث البصري (`visualIndex.js`):**

الخوارزمية: `local-color-spatial-edge-v1`
- تحويل الصورة إلى 32×32 بيكسل
- استخراج histogram اللون (64 قيمة)
- توزيع مكاني 4×4 (48 قيمة)
- كثافة الحواف HOG مبسط (128 قيمة)
- مجموع المتجه: 240 قيمة

**الحكم المستقل:** هذه خوارزمية تشابه بصري **بدائية ولكن أمينة**. تعمل على صور متطابقة أو متشابهة جداً. لا تفهم المحتوى الدلالي ("هذا حذاء رياضي") ولا تحقق هوية المنتج. الكود نفسه يوثق هذا:

```javascript
// dHash is diagnostic only; equality does not prove file/product identity.
exactMeaning: 'same_image_bytes_not_verified_product_identity'
```

**نقطة قوة:** الكود صادق تماماً في حدوده. هذا يحمي المنصة من ادعاءات مضللة.

**القيد الحرج:** `VISUAL_SEARCH_MAX_CANDIDATES = 5000` مع فحص كل مرشح (readLocalImage لكل مطابقة) — هذا **O(n)** على كل البيكسلات. مع نمو الكتالوج، سيصبح بطيئاً.

**AI للمورد (`productDraft.js`):**

الكود **ممتاز في تصميمه:**
- Claude يحلل الصورة ويقترح: عنوان، فئة، وصف مرئي فقط
- ممنوع صراحة: الأسعار، MOQ، المواد، المقاسات، الجودة، التوصيل
- `requiresSupplierReview: true` إلزامي
- `uncertainFields: ['price', 'currency', 'moq', 'unit', 'availability', 'materials', 'city']`
- عند فشل المزود: 503 مع الحفاظ على imageUrl والإدخال اليدوي

**المشكلة الوحيدة:** `providerConfigured()` يتحقق من `/^sk-ant-/` — المفتاح الحالي فارغ أو غير صالح.

### 4.2 مقارنة القدرات الحالية مقابل الرؤية المستقبلية

| الوظيفة | الحالة | الفجوة |
|---|---|---|
| رفع صورة المنتج من المورد | مكتمل | لا شيء |
| اقتراح عنوان/وصف/فئة بـ AI | مبني لكن معطل (401) | مفتاح Claude فارغ |
| منع اختلاق الأسعار | مكتمل ومُحكم | لا شيء |
| مراجعة المورد قبل النشر | مكتمل | لا شيء |
| رفع صورة من المشتري للبحث | مكتمل | لا شيء |
| بحث بصري دلالي (يفهم المحتوى) | **غير مبني** | يتطلب نموذج embedding (CLIP أو مماثل) |
| بحث في Jomla.ma أولاً ثم خارجياً | Jomla: مكتمل — خارجي: يحاكي | مفتاح Brave غائب |
| تجربة بحث ذكية بدون chatbot | مكتمل — الواجهة تعرض النتائج مباشرة | لا شيء |

### 4.3 مسار تطوير AI التدريجي المقترح

**المرحلة الصفر (الآن):** إصلاح مفتاح Claude — 1-2 ساعة عمل. كل الكود جاهز.

**المرحلة الأولى (v1.1):** اختبار AI بصور مصرح بها حقيقية للتحقق من جودة الاقتراحات.

**المرحلة الثانية (v2):** إضافة embedding دلالي. الخيار الموصى به:
- استخدام `sentence-transformers` (CLIP-like) محلياً — مجاني وخاص
- أو OpenAI embeddings API — مدفوع لكن أقوى

**المرحلة الثالثة (v3):** تحسين البحث النصي بـ semantic search بدلاً من text-match فقط.

## ملحق — تحقق مستقل من النقاط الثلاث المثارة (20 أكتوبر 2026)

### نقطة 1: URL Routing — الأدلة الفعلية

**ما فحصته:**
- `frontend/package.json` → لا وجود لـ `react-router-dom` أو أي مكتبة routing
- `frontend/src/App.js` → لا `BrowserRouter`، لا `Route`، لا `useNavigate`، لا `Link`، لا `window.history.pushState`
- `frontend/public/index.html` → عنوان: **"React App"** — لا `lang`، لا `dir`
- `frontend/build/index.html` → نفس الوضع في البناء الإنتاجي

**نتيجة البحث عن أي routing في ملفات src:**
```
Select-String -Pattern "react-router|BrowserRouter|HashRouter|useNavigate|useLocation" → لا نتائج
```

**التأثير المثبت بالكود:**

| السيناريو | ما يحدث |
|---|---|
| تحديث الصفحة (`F5`) | يعود المستخدم إلى الصفحة الرئيسية — يفقد موضعه |
| فتح رابط منتج | مستحيل — لا يوجد URL مخصص للمنتج |
| فتح رابط متجر | مستحيل — الانتقال يتم عبر `setSelection({storeId})` في state |
| زر الرجوع في المتصفح | يخرج من الموقع أو لا يفعل شيئاً |
| مشاركة رابط | يُشارك فقط الصفحة الرئيسية مهما كان المستخدم يشاهد |

**ملاحظة مصادة على تقرير السابق:** كنتُ قلت "لا `dir='rtl'` صريح". هذا **غير دقيق جزئياً**. `LanguageContext.jsx` يُعالج هذا بطريقتين:
1. `document.documentElement.lang = lang` و `document.documentElement.dir = lang === 'ar' ? 'rtl' : 'ltr'` — يُضاف لاحقاً عبر JavaScript
2. `<div dir={lang === 'ar' ? 'rtl' : 'ltr'}>` — يلف كل المحتوى

**الاستنتاج:** RTL مُعالَج برمجياً بعد تحميل الصفحة. المشكلة الحقيقية ليست dir بل أن `index.html` يحمل `lang="en"` ثابتاً للمحركات والبوتات ومدة ما قبل تحميل JS.

### نقطة 2: AI — تشخيص دقيق بلا استدعاء مدفوع

**الأدلة المجمعة:**

| الدليل | القيمة | المصدر |
|---|---|---|
| طول مفتاح Claude في `.env` | 23 حرفاً | فحص مباشر للملف |
| بداية المفتاح | `sk-ant-api` (أول 10 أحرف) | فحص مباشر |
| طول مفتاح Anthropic صالح | ~108 أحرف | توثيق Anthropic الرسمي |
| `providerConfigured()` | `return /^sk-ant-/.test(key)` | `productDraft.js` سطر 6 |
| نتيجة `providerConfigured()` | **true** — لأن المفتاح يبدأ بـ `sk-ant-` | منطق الكود |
| نتيجة الطلب الحي (19 أكتوبر) | **HTTP 401** | `pilot-evidence/ai-live-probe.json` |
| هل استُخدم المفتاح الحقيقي في الاختبار؟ | **لا** — `pilot-audit.js` يُعطّل dotenv ويضع `CLAUDE_API_KEY: ''` | `pilot-audit.js` سطر 7 |

**التشخيص الدقيق:**

`providerConfigured()` تعيد `true` لأن المفتاح يبدأ بـ `sk-ant-`. لكن المفتاح الحالي بطول **23 حرفاً** هو في الغالب **مفتاح مبتور أو مثال أو منتهي الصلاحية**. مفاتيح Anthropic الحقيقية تبدأ بـ `sk-ant-api03-` وتمتد لـ 108 أحرف تقريباً.

**الاستنتاج بدون استدعاء مدفوع:**
- المفتاح `sk-ant-api...` (23 حرفاً) لا يعمل — وهذا هو سبب الـ 401
- `providerConfigured()` ستعيد `true` (الكود يعتقد أن المزود متاح) لكن الطلب الفعلي يُرفض
- الخطأ ليس في الكود بل في **المفتاح نفسه** (مبتور أو منتهي الصلاحية أو خاطئ)
- لا يوجد في الكود أي طريقة للتحقق من صحة المفتاح قبل محاولة الاستدعاء الفعلي

**المطلوب من المالك:** مفتاح Anthropic Claude صالح وكامل. لا تعديل في الكود مطلوب.

### نقطة 3: Order.js — تحقق من العلاقة وسجل البيانات

**ما فحصته فعلاً في `rfq.js` (159 سطراً — قرأتها كاملة):**

عند **إرسال RFQ** (POST `/rfq`):
- يُنشأ `QuoteRequest` مع: buyerId، supplierId، productId، quantity، currency، status=`pending`
- يُنشأ `MessageThread` مرتبط بـ rfqId مع رسالة أولية

عند **إرسال عرض** (PUT `/rfq/:id/respond`):
- يُنشأ `QuoteOffer` مع: rfqId، supplierId، unitPrice، **totalPrice = unitPrice × quantity**، deliveryDays، paymentTerms
- يُحدَّث `QuoteRequest.status` إلى `responded` + `currentOfferId`
- يُضاف للـ MessageThread

عند **قبول العرض** (PUT `/rfq/:id/action`):
- يُحدَّث `QuoteRequest.status` إلى `accepted`
- يُحدَّث `QuoteOffer.status` إلى `accepted`
- يُغلق `MessageThread`
- **لا يُنشأ `Order` — إطلاقاً**

**أين يُستخدم Order.js فعلاً؟**

فقط في `suppliers.js` سطر 273-289:
- `GET /suppliers/me/orders` — يجلب طلبات من جدول Order
- `PATCH /suppliers/me/orders/:id/status` — يُغير حالة Order

**لكن:** لا يوجد `POST` ينشئ Order عند قبول عرض. جدول Order موجود، الـ endpoints موجودة، **لكنه مقطوع عن سير العمل الرئيسي**.

**ما هو محفوظ فعلاً؟**

عند قبول العرض، البيانات التالية **محفوظة ومثبتة** في:
- `QuoteRequest` → status=`accepted`، currentOfferId، quantity، currency، buyerId، supplierId، productId
- `QuoteOffer` → status=`accepted`، unitPrice، **totalPrice**، deliveryDays، paymentTerms، currency
- `MessageThread` → السجل الكامل للمحادثة + "تم قبول عرض السعر"
- `Notification` → سجل الحدث للمورد

**ما الوظيفة التجارية الناقصة بالضبط؟**

عدم وجود Order لا يعني فقدان البيانات. لكنه يعني:
1. **لا تجميع منظم للصفقات** — لا يستطيع المورد أن يرى "قائمة طلباتي المقبولة" دون مرور عبر RFQ
2. **لا حالة تسليم قابلة للتتبع** — QuoteOffer ليس له حقل "تم الشحن" أو "تم التسليم"
3. **لا سجل مستقل للمعاملات** — إذا أُلغي RFQ أو حُذف، لا يوجد سجل Order منفصل
4. `GET /suppliers/me/orders` يعيد قائمة **فارغة دائماً** لأن لا شيء يُنشئ Orders

**الاستنتاج المعدَّل:** بيانات RFQ والعرض المقبول **محفوظة بشكل كافٍ** لمرحلة التجربة الأولى. غياب Order مشكلة للمرحلة الثانية (تتبع التسليم، التقارير المالية)، ليست عائقاً للنسخة الأولى.
