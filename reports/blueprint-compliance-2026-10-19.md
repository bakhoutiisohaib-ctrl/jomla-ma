# تقرير مطابقة Jomla.ma للمخطط التأسيسي

تاريخ المراجعة: 19 أكتوبر 2026 — المرجع: المخطط التأسيسي 1.0 بتاريخ 18 أكتوبر 2026.

نسخة الشيفرة المفحوصة: 22da3d8. كان المستودع نظيفاً قبل المراجعة. المراجعة تشمل الشيفرة المحلية والاختبارات والبناء وفحوص API على قواعد MongoDB مؤقتة ببيانات وهمية.

## 1. الحكم التنفيذي

الإصلاحات والإضافات موجودة فعلياً، وأصبح المشروع نموذجاً برمجياً واسعاً للكتالوج وRFQ والإشراف، لكن المطابقة للمخطط جزئية. لا توجد أدلة كافية لاعتماد اكتمال MVP أو جاهزية تجربة ببيانات موردين ومشترين حقيقيين.

أهم موانع الاعتماد: تعديل الحسابات والترقية إلى مشرف دون مصادقة؛ كشف طلبات الأسعار والمحادثات وقبولها دون إثبات هوية المشتري؛ ظهور المسودات قبل اعتمادها؛ توليد بيانات تجارية مفترضة بواسطة بديل AI؛ وعدم اكتمال رحلة المشتري والمنظمات والمتاجر في الواجهة.

نجحت الاختبارات الحالية كلها: 34 اختباراً للخادم، واختباران للواجهة، ونجح بناء الإنتاج. لكن الفحوص الإضافية أثبتت عيوباً لا تغطيها تلك الاختبارات، وبعض الاختبارات الحالية يتوقع نجاح عمليات عامة يجب حمايتها. لذلك لا يصح تفسير نجاح الاختبارات على أنه تحقق شروط قبول المخطط.

لا أضع نسبة اكتمال إجمالية؛ لا توجد أوزان معتمدة للمتطلبات، ووجود ملفات أو أسماء كيانات لا يعادل رحلة مستخدم مكتملة وآمنة.

## 2. ما تم التحقق منه وحدود المراجعة

تمت قراءة وحدات الحسابات والكتالوج والذكاء الاصطناعي والبحث وRFQ والتوريد والإدارة والواجهات والترجمة، ومقارنة العقود بين API والواجهة، وتشغيل:

| الفحص | النتيجة |
|---|---|
| backend: npm test -- --silent | 7 مجموعات ناجحة، 34/34 اختباراً |
| frontend: CI=true، npm test -- --watchAll=false --runInBand | مجموعة ناجحة، 2/2 اختبار |
| frontend: npm run build | Compiled successfully |
| فحوص أمنية ووظيفية إضافية | نتائج HTTP وبيانات مخزنة على MongoDB مؤقتة؛ موضحة أدناه |

بناء الواجهة أظهر تحذيراً عن قدم بيانات Browserslist؛ لم يمنع البناء.

في فحوص API الإضافية عُطلت خدمات AI والتخزين السحابي داخل عملية الفحص، واستخدمت قواعد مؤقتة مستقلة، ثم أُغلقت. لم تُستخدم بيانات المستخدمين الحقيقية لإثبات الثغرات. توجد نسخة مختصرة من النتائج في [ملف الأدلة](C:/Users/hp/jomla-ma/reports/audit-evidence-2026-10-19.json).

لم يُنفّذ فحص متصفح شامل أو قياس على هواتف فعلية، ولا تجربة مع مورد غير تقني، ولا تقييم دقة بصري على مجموعة صور موسومة، ولا اختبار تحميل أو استعادة نسخ احتياطية. لم تُفحص بيئة إنتاج أو حسابات مزودي الخدمات. غياب مستند أو إعداد من المستودع يعني أنه غير مثبت في هذه المراجعة، وقد توجد ترتيبات خارج المستودع.

## 3. مطابقة قدرات MVP الثماني

| القدرة في المخطط | الموجود فعلياً | الحكم والفجوة |
|---|---|---|
| 1. حسابات وأدوار ومنظمات ومتاجر ومراجعة | تسجيل ودخول bcrypt/JWT؛ أربعة أدوار؛ ملف مورد؛ Store وAPI؛ مراجعة توثيق المورد | جزئي: Organization وMembership غير موجودين؛ صلاحيات الموظف غير منفذة؛ ثغرات تفويض؛ لا رحلة Store في الواجهة |
| 2. كتالوج جملة | Product؛ صور؛ MOQ؛ وحدة؛ شرائح أسعار؛ inStock؛ عملة افتراضية | جزئي: حقول النشر والحقوق غير مفروضة؛ الشرائح المتداخلة والمعكوسة مقبولة؛ لا نمط «اطلب سعراً»؛ إدارة التوفر والعملات ناقصة |
| 3. مسودة AI من صورة ومراجعة يدوية | مزود Claude اختياري؛ رفع صورة؛ مسودة؛ نموذج قابل للمراجعة؛ زرا المسودة والنشر | جزئي مع مخالفة صريحة: يخمّن أسعاراً وخصائص وتوفراً؛ البديل لا يقرأ الصورة؛ المسودة قد تظهر للعامة |
| 4. بحث نصي وفلاتر وبحث بالصورة | بحث regex ومرادفات؛ الصورة تتحول إلى كلمات؛ وسوم مطابق/مشابه | جزئي: فلاتر الواجهة ثابتة؛ لا معيار مثبت للمطابقة؛ لا مقارنة صور الكتالوج أو متجهات؛ ترقيم صفحات الصورة غير سليم |
| 5. RFQ وإشعارات وردود ومتابعة | إنشاء الطلب؛ لوحة المورد والرد؛ QuoteOffer؛ MessageThread؛ API للقبول والرسائل | جزئي: واجهة متابعة المشتري والمحادثة والقبول غائبة؛ إشعارات فعلية غير موجودة؛ التفويض غير كافٍ |
| 6. مشرف وتوثيق وبلاغات وتدقيق | لوحة مشرف؛ قبول/رفض المورد؛ بلاغات؛ سجل توثيق المورد | جزئي: سجل البلاغات يفشل؛ لا إجراءات فعلية لإشراف المنتج؛ التوثيق قابل للتجاوز بتعديل الحساب العام |
| 7. عربية وفرنسية وتجـاوب | LanguageContext؛ قاموس لغات؛ تبديل الاتجاه؛ بعض النصوص مترجمة؛ شبكات مرنة | جزئي: الرحلات الأساسية عربية ثابتة؛ تجاوب الهاتف غير مثبت باختبار |
| 8. بحث خارجي محدود بمصادر مسموحة | روابط Google Images/Shopping مع علامة خارجي وتجريبي وعدم التحقق | تمهيد فقط: لا جلب نتائج موردين عبر موصل فعلي، ولا حفظ اكتشافات أو سجل مصادر وشروط استخدام |

عدم وجود الدفع والضمان والشحن المدمج وERP وتطبيق جوال لا يُعد نقصاً في MVP؛ المخطط يؤجلها صراحة.

### رحلة المورد وإدارة الكتالوج

- تسجيل الحساب والملف والتوثيق موجودة مبدئياً؛ إنشاء Store مستقل غير موصول بالواجهة. لا توجد استدعاءات /stores في frontend/src.
- Product لا يتضمن storeId؛ صفحة كل متجر تجلب منتجات المورد كلها، لا كتالوجاً مخصصاً لذلك المتجر. راجع [stores.js:44](C:/Users/hp/jomla-ma/backend/routes/stores.js:44).
- لوحة المورد تجلب الصفحة الأولى من الكتالوج العام ثم تقارن p.supplierId === supplier._id، بينما API يعيد supplierId كائناً populated، واستجابة الدخول تستعمل supplier.id. النتيجة المتوقعة من هذا العقد: قائمة فارغة وإحصاءات خاطئة وطلب reviews/undefined. راجع [SupplierDashboard.jsx:45](C:/Users/hp/jomla-ma/frontend/src/components/suppliers/SupplierDashboard.jsx:45) و[suppliers.js:178](C:/Users/hp/jomla-ma/backend/routes/suppliers.js:178).

- Store.isVerified ينسخ توثيق المورد عند الإنشاء ولا يتزامن مع تغييره لاحقاً. isActive لا يُفحص في تفاصيل المتجر؛ تعطيله يخفيه من القائمة فقط.

| شرائح أسعار | تقبل نطاقات معكوسة ومتداخلة |
| موقع توريد | مدينة مطلوبة في المسار الأساسي؛ لا تصميم بلد/موقع دولي مكتمل |
| التوفر | boolean افتراضي true؛ لا إدارة مخزون أو سجل InventorySnapshot |
| المورد | يشتق في الإنشاء من التوكن؛ صلاحية حساب المورد نفسه غير مفروضة |

ثبت قبول minQty=100 وmaxQty=2، مع شريحة أخرى تتداخل معها. وثبت إنشاء RFQ بكمية 1 لمنتج MOQ=10. يجب ضبط سياسة النطاقات وربط التحقق بالكمية المقبولة أو تعريف تفاوض الاستثناء صراحة.

### رحلة المشتري وRFQ

نموذج إنشاء الطلب ورد المورد موجودان. لكن واجهة RFQModal تنتهي برسالة نجاح ورقم مختصر ورابط واتساب، ولا توفر سجل مشتريات/طلبات للمشتري أو إعادة فتح الطلب أو مشاهدة العرض وقبوله أو المحادثة داخل المنصة. API لهذه الوظائف موجود جزئياً دون واجهة تستدعي /action أو /thread أو /messages.

لا توجد إشعارات فعلية بالبريد أو SMS أو push أو websocket أو نظام Notification؛ عدادات لوحة المورد تُجلب عند فتحها. إنشاء رسالة في قاعدة البيانات لا يحقق تنبيه المستخدم.

الحالة accepted تظهر في لوحة المورد على أنها «مرفوض» لأن العرض يعالج pending/responded فقط. راجع [SupplierDashboard.jsx:672](C:/Users/hp/jomla-ma/frontend/src/components/suppliers/SupplierDashboard.jsx:672).

كل رد جديد ينشئ QuoteOffer فعالاً دون إبطال السابق. في الفحص بقي عرض قديم active بعد قبول الأخير. القبول لا يحدد offerId صريحاً، ومسار الرد يسمح بإعادة تعديل طلب انتهى، وأي action غير accept يُفسر رفضاً. يلزم ضبط انتقالات الحالات وربط القرار بعرض محدد ومعالجة القيم غير الصحيحة.

### طلب التوريد

الإنشاء موجود، لكن [sourcing.js:94](C:/Users/hp/jomla-ma/backend/routes/sourcing.js:94) يزيد quotesCount ويغير الحالة إلى quoted فقط. السعر ومدة التسليم والملاحظات وهوية المورد لا تُحفظ كعرض مستقل، بل تُوضع في رابط واتساب.

بعد أول عرض يختفي الطلب من قائمة المورد التي تجلب status=open، فلا تتحقق المقارنة بين عروض متعددة في الرحلة المعتادة. ورابط إدارة التوريد يستخدم رقماً تجريبياً ثابتاً 212600000000. المطلوب حفظ العروض والمتابعة وإبقاء الطلب مفتوحاً للمنافسة حتى إغلاقه وفق سياسة واضحة.

## 6. البحث والذكاء الاصطناعي والمصادر الخارجية

### البحث النصي والفلاتر

البحث النصي وقاموس المرادفات وبعض التعامل مع الدارجة موجودة. تحمي escapeRegex المدخلات في المسارات التي تستخدمها، ونجحت الاختبارات الخاصة بالأحرف الخاصة.

لكن [App.js:28](C:/Users/hp/jomla-ma/frontend/src/App.js:28) يعرف filterCity/filterCategory/filterPrice بقيم فارغة دون setters، فلا توجد فلاتر قابلة لتغيير المستخدم في الرحلة الحالية. API البحث الذكي يدعم المدينة والفئة جزئياً؛ لا يقدم فلترة كمية/مورد/حد سعر متكاملة. لا توجد مقارنة منتجات في الواجهة.

وسم «مطابق» في البحث النصي يعتمد على احتواء الاسم أو الاستعلام أحدهما الآخر، ولا توجد إعادة ترتيب صريحة لكل النتائج لتقديم المطابق على المشابه. راجع [aiSearch.js:123](C:/Users/hp/jomla-ma/backend/routes/aiSearch.js:123).

### البحث بالصورة

المسار الفعلي هو صورة ← كلمات عبر Claude/Google Vision عند توفرهما ← regex على أسماء وفئات المنتجات. لا يقارن صور المنتجات بعضها ببعض ولا يخزن تمثيلات بصرية.

في [imageSearch.js:123](C:/Users/hp/jomla-ma/backend/routes/imageSearch.js:123)، أي تطابق مع كلمة في الاسم أو الفئة يكفي لوضع matchType=exact. هذا لا يثبت أن المنتج هو نفسه في الصورة. وعند تعذر المزود يستخرج البديل كلمات من اسم الملف في السطر 98؛ لا يصح عرض ذلك كفهم بصري مؤكد.

هناك خلل pagination: يجلب المسار limit من كل مجموعة ثم يطبق slice باستخدام skip؛ لم تُجلب الصفحة التالية من قاعدة البيانات أصلاً، وtotal يمثل النتائج المحملة بعد الحد لا إجمالي التطابقات. راجع [imageSearch.js:135](C:/Users/hp/jomla-ma/backend/routes/imageSearch.js:135) و[imageSearch.js:185](C:/Users/hp/jomla-ma/backend/routes/imageSearch.js:185).

عدم وجود متجهات ليس وحده إخلالاً، لأن المخطط يقترحها تدريجياً. النقص الأساسي هو غياب تعريف يمكن اختباره للمطابق/المشابه وقياس واقعي لدقتهما وتوضيح حالات تعذر التحليل.

### البحث الخارجي

الإيجابي: توضع علامة «خارجي - تجريبي» وتنبيه عدم التحقق، وتحتوي البيانات isVerified:false.

الموجود في [imageSearch.js:210](C:/Users/hp/jomla-ma/backend/routes/imageSearch.js:210) روابط بحث Google مولدة. لا يوجد جلب فعلي لنتائج موردين أو adapter لمصدر اكتشاف معتمد. ExternalDiscoveryResult نموذج مستورد دون استخدام للحفظ في هذا المسار.

الواجهة تعرض القسم عند وجود الكائن دون فحص enabled، ولا تمسح دائماً اكتشاف البحث السابق عند بحث نصي جديد؛ قد تبقى روابط تخص بحثاً قديماً. راجع [App.js:526](C:/Users/hp/jomla-ma/frontend/src/App.js:526).

يوجد أيضاً موصل صور Pexels اختياري، لكنه لا يثبت مطابقة صورة المخزون للسلعة التي يبيعها المورد، ولا تحفظ دورة المنتج ترخيصاً ومصدراً موثقين. لم أقيّم شروط استخدام Google أو Pexels قانونياً؛ المطلوب هنا سجل مصادر وطرق استخدام وأدلة موافقة قابلة للمراجعة، لا افتراض المنع أو السماح.

## 7. الإشراف واللغات والتشغيل

### الإشراف والثقة

إرسال ملف التوثيق ومراجعة المشرف وقرار القبول/الرفض وتسجيل أحداث هذه القرارات موجودة. ذلك يمثل تقدماً واضحاً.

لكن التحقق من ICE/RC هنا إدخال ومراجعة داخلية؛ لا دليل على تحقق مستقل من سجل رسمي. لا توجد دورة إشراف منتجات لتعليق منتج أو إزالته بقرار إداري موثق. حل البلاغ يغير حالته وملاحظاته فقط، ولا يربط القرار بإجراء على المنتج أو المورد. أسماء PRODUCT_MODERATED وPRODUCT_DELETED معرفة في نموذج السجل دون مسارات تستخدمها، وحذف المنتج الحالي لا يكتب AuditLog.

### اللغتان والهاتف

LanguageContext يحفظ اللغة ويغير lang وdir بشكل صحيح مبدئياً. الاستخدام الفعلي للترجمة محصور عملياً في App وReportModal؛ الدخول والتسجيل وبطاقات المنتج وRFQ والتوريد ولوحتا المورد والمشرف عربية ثابتة، وبعض المكونات تفرض rtl.

التجاوب يملك أساساً من الشبكات المرنة والنوافذ، لكن لا يمكن اعتماد «هاتف أولاً» دون فحص العرض والتفاعل على مقاسات هاتف فعلية. لم تُنفذ هذه الخطوة في المراجعة.

### الحماية والتشغيل

الموجود: Helmet، rate limiting عام، حدود JSON، bcrypt، JWT، فحوص لبعض المدخلات، سجلات Winston/Morgan، Redis cache اختياري، Swagger، وCloudinary اختياري مع تخزين محلي بديل.

الفجوات المثبتة:

- [upload.js:19](C:/Users/hp/jomla-ma/backend/middleware/upload.js:19) يثق في MIME المقدم من العميل، ويحتفظ بالامتداد الأصلي، ولا يحدد fileSize. حد JSON لا يحمي multipart.
- مسارا productAI وimageSearch يحددان 10MB لكن لا يفحصان صلاحية محتوى الصورة أو بصمتها. فحص AI الإضافي قبل bytes غير صورية.
- [suppliers.js:369](C:/Users/hp/jomla-ma/backend/routes/suppliers.js:369) و382 يستدعيان ObjectId دون new. ثبت أن analytics يعيد 500 ورسالة Class constructor ObjectId cannot be invoked without 'new'.
- CORS_ORIGIN في .env.example قائمة مفصولة بفاصلة، بينما [server.js:25](C:/Users/hp/jomla-ma/backend/server.js:25) يمررها كسلسلة واحدة. عند محاكاة المثال عاد Access-Control-Allow-Origin بالقيمتين معاً، وهو إعداد لا يسمح للمتصفح بمطابقة Origin واحد. هذا يخص صيغة المثال؛ لم أفترض أن إعدادك الفعلي مطابق له.
- تسجيل الخروج في App يمسح الحالة فقط ولا يحذف supplierToken من localStorage. وتقبل لوحة المشرف supplierToken كبديل؛ يلزم إنهاء الجلسة المخزنة بوضوح.
- لا توجد queue للمهام الثقيلة أو طبقة موحدة لمزودي AI أو إعدادات نسخ احتياطي واستعادة أو CI ضمن الملفات المتتبعة. Redis المستخدم cache، وليس دليلاً على تنفيذ queue.

## 11. خطة الإغلاق بالترتيب

1. قبل أي بيانات حقيقية: إغلاق تعديل المورد العام وإعداد المشرف المفتوح؛ حماية RFQ والرسائل وبيانات التوريد؛ إصلاح سحب الأدوار وفصل الملف العام عن البيانات الخاصة.
2. ضبط نشر المنتج: إخفاء المسودات في كل المسارات؛ فرض متطلبات النشر والحقوق؛ إيقاف التخمين التجاري في AI؛ التحقق من ملفات الصور.
3. إكمال العلاقات والواجهات: منظمة وعضوية وصلاحيات؛ رحلة Store؛ إصلاح id/_id وقائمة منتجات المورد؛ إدارة التوفر وحقول الكتالوج والأسعار.
4. إكمال التجارة: سجل طلبات للمشتري؛ عروض محددة ومحادثة وقبول وحالات متسقة؛ إشعارات؛ حفظ عروض التوريد والمقارنة بينها؛ إصلاح سجل البلاغات وإجراءات الإشراف.
5. استكمال البحث واللغات: فلاتر فعالة؛ معيار مطابق/مشابه؛ pagination سليمة؛ فرنسية كاملة؛ موصل خارجي تجريبي ضمن مصادر معتمدة مع حفظ مصدر النتيجة وعلامتها.
6. اعتماد التشغيل والتجربة: قرار معماري مكتوب؛ إعداد CORS؛ معالجة analytics؛ نسخ واستعادة مختبرة وقياس وتنبيه؛ ثم اختبارات القبول ومقابلات وتجربة مغربية محدودة.

نتيجة الاعتماد الحالية: المطابقة جزئية، والأساس البرمجي قابل للاستكمال، لكن شروط القبول الوظيفية والأمنية لم تتحقق بعد. اقتصر التغيير في هذه المهمة على إنشاء التقرير وملف أدلته؛ لم أغيّر منطق التطبيق.
