# JOMLA.MA — Reliability R2: إنشاء RFQ دون تكرار واستكمال المحادثة

التاريخ: 22 أكتوبر 2026، Europe/Paris. النطاق: **P1-02 فقط**. المراجع: تدقيق D3، تقرير R1 وتقرير Phase B. لا تتضمن الجولة R3 أو R4 أو الدفع أو المحفظة أو العربون.

## النتيجة

نُفذ إنشاء RFQ بمعرف محاولة ثابت، وسجل إنشاء داخل الطلب نفسه، وحالة `creating` صريحة. لا يصبح الطلب جاهزاً للتفاوض ولا يرجع201 قبل حفظ المحادثة ورسالتها الأولى وإشعار المورد والتحقق منها. فشل أثر لاحق يرجع202 قابلاً للاستكمال بدلاً من إعلان فشل الإنشاء أو نجاحه النهائي.

**R2 مكتملة وقابلة للاعتماد محلياً ضمن حدود التعافي والتوافق الموثقة.** أثبتت الاختبارات المستقلة طلباً واحداً ومحادثة واحدة وإشعار إنشاء واحد عند التزامن وفقد تأكيد الكتابة وإعادة تشغيل عملية الخادم. بقي بروتوكول قبول/رفض Phase B وسجل الاتفاق المثبت كما هما. نجحت309/309 للخلفية و159/159 للواجهة وبناء الإنتاج النهائي؛ لا ادعاء بتجربة استضافة أو أجهزة مادية.

- حُفظت نسخ ملفات R2 المحدودة **قبل تعديل كل منها**، بما فيها الملفات غير المتتبعة، خارج شجرة المشروع في `C:\Users\hp\AppData\Local\Temp\jomla-r2-source-89e3e4049b39443ea5de172368327148`. ## إثبات المشكلة قبل الإصلاح

كان POST يحفظ `QuoteRequest` ثم `MessageThread` ثم `Notification` بكتابات مستقلة. لم توجد هوية محاولة أو حالة إنشاء وسيطة. فشل المحادثة بعد حفظ الطلب أعطى500 بينما بقي RFQ في `pending`، ثم أنشأ تكرار الطلب مستنداً جديداً.

في إعادة إنتاج معزولة على Mongo standalone: بعد الفشل كان **RFQ واحداً وصفر محادثات وصفر إشعارات**، وبعد الإعادة201 بقي **RFQان ومحادثة واحدة وإشعار واحد**. بقي الطلب الأول يتيماً. أُرسل حتى المفتاح نفسه إلى المسار القديم، الذي كان يتجاهله. [before-thread-failure.json](phase-r2-evidence/before-thread-failure.json)، والمشغل [before.cjs](phase-r2-evidence/before.cjs).

## آلية الاتساق ومنع التكرار

1. يولد نموذج Atlas مفتاحاً آمناً عبر Web Crypto لكل إرسال جديد صريح، ويحتفظ بنسخة JSON مطابقة لما أُرسل. الإعادة تستخدم **المفتاح والجسم الأصليين**؛ لا يُولد مفتاح جديد هرباً من نتيجة غير محسومة.
2. تُربط الهوية بالمشتري المصادق عليه حياً. SHA256 تُحسب على معرفه والمدخلات المعتمدة بعد تحويل الكمية والسعر إلى أرقام وتطبيع النصوص. لا سلطة لحقول buyerId أو supplierId أو status أو creation المزورة. اختلاف المحتوى المقبول مع المفتاح نفسه يعطي409.
3. يتضمن إدراج RFQ الأول نفسه `creation.version=1` ومفتاحاً وبصمة وحالة pending ومعرفين ثابتين للمحادثة والإشعار، وعنوان المحادثة ومحتوى رسالتها الأولى الملتقطين عند الإرسال. لا توجد نافذة بين حفظ RFQ وحفظ سجل عملية منفصل.
4. فهرس فريد جزئي `rfq_creation_buyer_key` على `buyerId + creation.key` يمنع إدراج طلبين. يتحقق المسار من وجوده وتغطيته الفعلية، ويفشل503 عند غيابه بدلاً من الوعد بضمان غير موجود. سباق الإدراج أو فقد تأكيده يعقبه بحث عن الطلب تحت **المشتري والمفتاح نفسيهما** وفحص البصمة.
5. يبدأ الطلب في `status=creating` وrevision-1، ولا تقبل حراس الحالة الموجودة عرضاً أو رسالة أو قراراً عليه. يستخدم الاستكمال `$setOnInsert` بمعرفات `_id` المحفوظة للمحادثة والإشعار؛ معرف الرسالة الأولى ثابت أيضاً. لا تُستبدل رسائل أو حالة إغلاق أو `readAt` عند الإعادة.
6. بعد إثبات المحادثة وأطرافها ورسالتها وإشعار المورد، يُنشر `status=pending` و`creation.phase=completed` **أخيراً**، ويصبح revision0 كما كان قبل R2. تبدأ مراجعات Phase B من القيمة السابقة نفسها؛ سجل `decision` وخوارزمية الاتفاق لم يتغيرا.
7. كل كتابات الإنشاء وآثاره تطلب `writeConcern:{w:1,j:true}` وmaxTimeMS10000. لا replica set ولا معاملات متعددة المستندات. أُثبت standalone وغياب setName، والتُقطت أوامر Mongo الفعلية: [mongo-write-concern.json](phase-r2-evidence/mongo-write-concern.json).
8. إذا تعذر أثر بعد النية المحفوظة، يعاد202 مع `processing:true` وRFQ في creating، ولا يعاد threadId جاهز. إذا نجحت الكتابة النهائية وضاع تأكيدها، تعاد القراءة ولا تُعلن نتيجة جزئية خطأً.
9. الاستكمال إما بإعادة POST بالمفتاح نفسه، أو `POST /api/rfq/:id/creation/retry` من المشتري المالك، أو عامل الخلفية. الاستكمال بمعرف الطلب لا ينشئ طلباً جديداً ولا يحتاج إعادة محتوى العميل.
10. يقرأ العامل فقط creating/version1/pending؛ يعالج25 سجلاً مستحقاً كل5 ثوانٍ، ويؤخر الفشل تدريجياً حتى60 ثانية. يبدأ مع API ومع العامل المستقل، ويقبل تعدد النسخ والإغلاق الهادئ. إنه استكمال أثر مخول سبق حفظه، وليس إرسال RFQ جديد تلقائياً.

حذف المنتج أو تغيير اسمه بعد حفظ النية لا يستدعي تخمين عنوان جديد للمحادثة أو إعادة تحديد المورد؛ الاستكمال يعتمد السياق المحفوظ. إعادة POST بعد قبول اتفاق ترجع الطلب الأصلي **بحالته التجارية الحالية** ولا تعيده إلى pending ولا تفتح محادثته.

## واجهة المستخدم

- بقي مدخل RFQ ومسار العودة من تسجيل الدخول في C2. فتح النموذج أو تسجيل الدخول لا يرسل شيئاً تلقائياً؛ نجح اختبار العودة الفعلي واختبار routing الآلي.
- النموذج يستخدم AtlasDialog الموجود، مع التركيز وEscape ولوحة المفاتيح، ويحافظ على الحقول العربية/الفرنسية وRTL/LTR والهاتف.
- نتيجة الشبكة أو500 غير المحسومة تُظهر تفسيراً واضحاً وتمنع تعديل الجسم والنقر المكرر والإغلاق غير المقصود حتى استكمال المحاولة الأصلية. لا تُعرض رسالة «أُرسل الطلب» قبل تأكيد الجاهزية.
- عند202 بمعرف معلوم يمكن الإغلاق؛ تعرض «طلباتي» حالة «طلب قيد الإنشاء» وزر الاستكمال، حتى بعد تحديث الصفحة. لا يظهر زر التفاوض حتى الجاهزية. أُدرجت creating في تصفية الاستكمال وعداد ما يحتاج مراجعة.
- زر الاستكمال في السجل يعيد الطلب الموجود فقط. فشل آخر202 يبقي الحالة غير مكتملة. النقر المزدوج محمي بقفل متزامن، وليس بحالة React وحدها.
- نسخة النموذج مرتبطة بالجلسة والمنتج، وتُلغى الطلبات عند تبديل الحساب. لا يطبق رد متأخر نتيجة الحساب السابق. لا تُملأ حقول حساب جديد بملف مستخدم قديم أثناء تحميله.
- لا JWT أو جسم RFQ في URL أو تخزين متصفح جديد. المفتاح والجسم في ذاكرة النموذج؛ لا إقرارات أو إرسال نيابة عن المستخدم.

## API والبيانات والتوافق

| التغيير | العقد |
|---|---|
| `Idempotency-Key` اختياري على POST | 16–128 حرف ASCII من الأحرف/الأرقام/`_`/`-`؛ الواجهة الحالية ترسله دائماً |
|201 | processing:false، RFQ الأصلي، threadId، ملخص creation version/phase/replayed |
|202 | processing:true وstatus creating؛ النية محفوظة لكن المحادثة/الإشعار غير مكتملين |
| استكمال بالمعرف | POST `/:id/creation/retry`، مشتري المالك فقط؛ حساب آخر403، سجل تاريخي بلا journal409 |
| قوائم الطلبات | المشتري يرى creating ليستكمله؛ قائمة المورد تستبعده حتى الجاهزية؛ قراءة المحادثة أثناءه202 وthread:null |
| بيانات إضافية | journal اختياري مخفي، حالة creating، revision-1 أثناء الإنشاء فقط، فهرس فريد جزئي وفهرس فحص الاستكمال |

تبقى استجابات النجاح السابقة متوافقة قدر الإمكان مع إضافة processing وملخص creation. المفاتيح والبصمات وسجل الاستكمال الداخلي لا تُسلسل ضمن RFQ. MessageThread وNotification لم يحتاجا تغيير مخطط أو فهارس جديدة؛ استُخدمت فهارس `_id` ومعرفات ثابتة.

**العملاء القدامى دون header:** تبقى القدرة الأساسية على الإنشاء؛ يحصل كل POST جديد على نية داخلية قابلة للاستكمال بواسطة المعرف والعامل. لكن إعادة POST دون مفتاح بعد ضياع الرد **لا يمكن ربطها بمحاولته السابقة وقد تكرر RFQ**. يجب تحديث هؤلاء العملاء لإرسال المفتاح، أو مراجعة السجل واستكمال المعرف الموجود. لا ندعي منع تكرار طلبين بمفتاحين مختلفين أو عميل لا يرسل هوية المحاولة.

لا backfill أو ترحيل أو حذف بيانات أصلية. السجلات التاريخية بلا journal خارج الفهرس الجزئي والفحص التلقائي؛ اليتيم التاريخي لا تُنشأ له محادثة عشوائية.

## فحص المتصفح الفعلي

استخدمت بيئة loopback5070، بحسابات buyer/supplier/buyer2 اصطناعية وMongo مؤقتة وملفات رفع/سجلات في TEMP. استُخدم المتصفح الفعلي بحاسوب1440×1000 وهاتف محاكى390×844؛ لم تُستخدم قاعدة أصلية.

1. زائر فتح المنتج ← RFQ ← الدخول ← العودة إلى النموذج. لقطة قاعدة قبل ضغط الإرسال أثبتت صفرRFQs/محادثات/إشعارات؛ لا إرسال تلقائي.
2. حُجب حفظ المحادثة فظهر202 ومعرف الطلب، دون رسالة نجاح. بقي الطلب creating ومحادثاته وإشعاراته صفراً. أُغلق النموذج بعد معرفة المعرف، وظهر الاستكمال في السجل بعدF5. محاولة أثناء العطل بقيت202، ثم أُطلق العطل واستُكمل **المعرف نفسه** بزر Enter.
3. أُرسل RFQ جديد بكمية30، وأُسقط201 بعد اكتماله. عرضت الواجهة النتيجة غير المحسومة والجسم المجمد؛ أعاد الاستكمال الطلب نفسه دون نسخة ثانية.
4. ظهر للمورد طلبان وإشعارا إنشاء فقط. فتح الطلب ذي30، وأرسل رسالة وعرضاً110MAD/زوج، إجمالي3300، مهلة4 أيام وشروطاً اصطناعية. عاد المشتري الأصلي، ورأى رسائل الطرف الصحيح وعرضه الحالي، وأرسل رداً ثم قبل بعد تأكيد صريح.
5. ظهرت بيانات الاتفاق المثبتة وأُغلقت المحادثة، مع النص الواضح أن القبول لا يؤكد دفعاً أو شحناً أو تسليماً. ثم خرج المشتري A ودخل B؛ ظهرت قائمة فارغة وإشعارات0، دون طلبات أو بيانات اتفاق A.

## حدود التعافي وشروط التشغيل المستقبلية

1. يلزم تخزين Mongo يدعم journaling، وفهرس فريد مطابق قبل قبول إنشاء الطلبات. مع autoIndex:false يُنشأ الفهرس بإجراء تشغيلي معتمد لاحقاً؛ لم يُنشأ على القاعدة الأصلية في هذه الجولة. غيابه503، وتعطيل journal ليس بديلاً لتجاوز الضمان.
2. يلزم تشغيل عامل الاستكمال مع API أو worker بعد إعادة التشغيل وبعد restore. مجرد استيراد `server.js` لا يبدأه. راقب عمر pending وعدد المحاولات ورموز RFQ_CREATION_RETRY/CONFLICT، وحمل backlog مع حد25/دورة. لا ادعاء باختبار حمل إنتاجي.
3. إذا تعطلت القاعدة بحيث تعذرت الكتابة والقراءة معاً، تبقى نتيجة العميل غير محسومة حتى عودة الخدمة. يعيد المفتاح نفسه؛ لا يفترض الفشل ولا يولد مفتاحاً جديداً. استمرار عطل أو تعارض بيانات يبقي creating ويحتاج مراجعة؛ لا توجد تسوية تخمينية.
4. المفتاح والجسم في ذاكرة النموذج، ويُفقدان عند إعادة تحميله أو تبديل الحساب. تاريخ الطلبات والعامل يتيحان استكمال النية التي حُفظت حتى بعد ذلك. إذا لم يعلم العميل المعرف، يراجع طلباته قبل إنشاء محاولة جديدة؛ لا مطابقة تخمينية بالاسم/الكمية.
5. الضمان طوال بقاء الطلب وسجل الإنشاء، دون TTL. إزالة المستند/سجله خارج النظام أو استعادة غير متسقة للمجموعات ليست عملية إعادة محاولة مدعومة. تُستعاد QuoteRequest/MessageThread/Notification والفهارس معاً ثم يعمل الاستكمال؛ لم تُنفذ استعادة أصلية أو ترحيل.
6. الآثار قابلة للإعادة بأمان، وليست معاملة متعددة المستندات أو exactly-once لكل رسالة لاحقة. إصلاح تكرار عرض المورد R3 ومحدد المعدلR4 مؤجلان عمداً. لم تُستبدل آلية Phase B أو تُغيّر اتفاقات قديمة.
7. العملاء القدامى بلا مفتاح خارج ضمان ربط POST المعاد. والسجلات التاريخية اليتيمة تبقى كما هي. إن أراد المالك معالجة تاريخية فتلزم جولة معتمدة مستقلة بأدلتها.
8. الاختبار محلي؛ لم تُفحص استضافة أوproxy حقيقي أو هاتف مادي. حفظ ملفات TEMP طويل الأجل وتهيئة الفهارس والمراقبة والنسخ التشغيلية قرارات قبل الإطلاق، لا نشر ضمنR2.

## التراجع والإقفال

قبل التراجع يجب تصريف نوايا creating أو إيقافها ومراجعتها مع إبقاء journal. تُستعاد ملفات R2 المحدودة من نقطة الحفظ، وتُترك الحقول والفهارس والبيانات الإضافية سليمة. لا حذف طلبات ولا إسقاط فهارس ولا تغيير creating إلىpending يدوياً. الشيفرة القديمة لا تفهم creating وتعيد خطرP1-02؛ لا يُعتمد تراجع يتجاهل النوايا المعلقة.

سجل سلامة الملفات والاختبارات النهائي: [final-verification.json](phase-r2-evidence/final-verification.json). بالمقارنة مع3897 ملفاً من الحالة السابقة، تغيرت12 نسخة موجودة ضمن القائمة المحفوظة فقط؛ **صفر تغيير غير متوقع وصفر ملف مفقود**. تحققت بصمات النسخ المحدودة والأرشيف السابق، وبقي HEAD وفهرس Git دون تغيير، ونجح `git diff --check`.

**العمل متوقف بعدR2، بانتظار موافقة المالك قبلR3.** لا Commit أوPush أو نشر أو تعديل أسرار أو استخدام قاعدة أصلية.
