# Jomla.ma — R4-3B / S3: Sourcing Decision Reliability

التاريخ: 2026-10-26. **S3 فقط، محلياً. الحكم: PASS في البيئة المعزولة. البيئة الأصلية NOT ACTIVATED / NOT VERIFIED.**

## 1. المشكلة والنطاق

كان مسار قرار المشتري يغيّر العرض إلى accepted/rejected، ويغيّر الطلب إلى fulfilled عند القبول، ثم يحفظ SourcingRequest، وبعد ذلك ينشئ Notification منفصلاً. فشل الإشعار بعد الحفظ أو فقد تأكيد HTTP لا يملك إيصالاً دائماً أو نية استكمال؛ الإعادة تصطدم بعرض لم يعد active. الدليل على ترتيب الكتابات محفوظ في نسخة المسار قبل S3، داخل النسخة المحدودة الخارجية.

المراجع: [S2](C:/Users/hp/jomla-ma/reports/phase-r4-3b-s2-sourcing-offer-reliability.md)، و[خطة R4-3B](C:/JomlaVerification/R4-3B-analysis-20261025T130307Z/phase-r4-3b-sourcing-reliability-audit-plan.md). تشخيصات التدقيق السابقة كانت تثبت السلوك المعيب، ولم تُعدّل أو تُحتسب ضمن اختبارات الإصلاح.

لا تغيير لبروتوكولات RFQ أو المنتجات أو الصور أو الكتالوج أو سياسات الموردين. لا محادثة أو Order أو دفع/شحن جديد، ولا تحديث تبعيات أو Migration/Backfill أو اتصال بالقاعدة الأصلية أو Commit/Push/نشر.

## 2. البروتوكول المنفذ

أضيفت حقول اختيارية داخل SourcingRequest فقط: operation.kind=sourcing_decision/version1، وإيصال decisionReceipt دائم داخل العرض، وagreement مثبت عند القبول. تبقى السجلات القديمة بلا هذه الحقول، وتحفظ إيصالات S1/S2.

1. **الهوية الطبيعية** هي المشتري المصادق عليه المالك + الطلب + quoteId؛ الفعل الأول accept/reject ثابت. لا مفتاح Idempotency-Key جديد للقرار. يفحص الإيصال أولاً، قبل الحالة التجارية وأي عملية أخرى. الإعادة المكتملة تعيد العرض الحالي وملخص القرار دون أثر جديد؛ المعلقة تستكمل النية نفسها؛ الفعل المعاكس409. إيصال قديم لا يستكمل عملية أحدث.
2. **حجز ذري** بغياب operation وCAS على __v والحالة والعرض active. يثبت هويات الطلب والمشتري والفاعل والمورد والعرض، والفعل، والمدخلات التجارية ومصدرها، وبصمة الحالة، ومعرفي العملية والإشعار، والنسخة المتوقعة. لا ينشر accepted/rejected/fulfilled أثناء الحجز.
3. يتحقق المعالج المستقل من kind/version/phase والملكية والهوية وصلاحية المشتري الحالية والنسخة التجارية قبل الأثر والنشر. يستعمل إشعار sourcing_decision الموجود بمعرف ثابت و$setOnInsert، ثم يقرأه من primary ويتحقق من المستلم والنوع والطلب والتوقيت وعدم إسناده لقرار RFQ آخر. نص الإشعار الحالي مشتق من النوع والطلب، وليس مدخلاً موثوقاً من العميل؛ لم يُختلق محتوى أو نوع جديد. readAt محفوظ.
4. **كتابة تجارية واحدة محمية** تكتب الإيصال والاتفاق عند القبول، وتحدّث الحالات والعداد، وترفع النسخة وتزيل operation. استُعمل تحديث native للحفاظ على الحقول التاريخية غير المعروفة في العروض، مع التحقق من النية والبيانات قبل الكتابة.
5. القبول يجعل العرض accepted والطلب fulfilled بمعنى **اختيار العرض فقط**؛ بقية active تصبح superseded والعداد0. الرفض يغيّر العرض المعني فقط إلى rejected، ويحفظ حالة الطلب السابقة open/quoted وبقية العروض الفعالة ويعيد حساب العداد. يمكن اتخاذ قرار لاحق على عرض آخر.
6. أخطاء الكتابة وفقد تأكيدها تُحسم بقراءة النية أو الإيصال من primary؛ لا يُعتبر خطأ الكتابة إثباتاً منفرداً للفشل أو النجاح. الكتابات تطلب w:1,j:true. لا معاملات Mongo متعددة المستندات ولا قفل ذاكرة للصحة.

الحجز المشترك عبر operation وCAS يمنع سباق S2/S3 وقرارين مختلفين. تغيير S2 محدود بحارس نوع العملية عند retry؛ لا إعادة كتابة لبروتوكول العرض أو إنشاء الطلب.

## 4. API والخصوصية والواجهة

| المسار/الحالة | العقد |
| --- | --- |
| PUT /api/sourcing/:id/quotes/:quoteId/action | الجسم الحالي action؛ لا مفتاح جديد |
| 200 / processing:false | قرار مؤكد، ملخص decision آمن، واتفاق عند القبول |
| 202 / processing:true | نية محفوظة قيد الاستكمال، دون نجاح نهائي |
| 409 SOURCING_DECISION_ACTION_CONFLICT | إجراء معاكس لإجراء مثبت |
| 409 SOURCING_OPERATION_PENDING | عملية متعارضة قيد الاستكمال |

| 413 SOURCING_DOCUMENT_CAPACITY قبل الحجز | لا نية أو إشعار جديد |
| POST /api/sourcing/:id/operations/:operationId/retry | المشتري المالك يستكمل decision فقط؛ المورد/الموظف المخول يستكمل offer فقط؛ الجسم لا يبدل الفعل أو السعر |

DTOs صريحة تُظهر ملخص pending، وتفاصيل decisionRecovery للمشتري المالك فقط، وofferRecovery وفق صلاحيات S2 فقط. لا raw operation/decisionReceipt أو مفاتيح أو بصمات أو بيانات منافسين. القبول لا يضيف صلاحية اتصال المشتري، وbuyerId داخل نسخة الاتفاق لا يظهر للمورد. أضيف إخفاء دفاعي للإيصال وهوية المشتري داخل الاتفاق عند تحويل المستند أيضاً.

بطاقة القرار المنفصلة تحفظ Atlas وRTL/LTR؛ تمنع الضغط المزدوج والقرارات البديلة أثناء عدم الحسم، وتعيد الفعل الطبيعي نفسه أو operationId المحفوظ.202 لا يعرض نجاحاً نهائياً. عند إعادة الفتح تُقرأ العملية المحفوظة دون إرسال قرار تلقائي؛ يمكن تحديث القراءة أو الاستكمال الصريح. إشعار المورد السابق للنشر يفتح الطلب المخول ويعرض أن القرار قيد الاستكمال؛ العرض يبقى active حتى النشر.

المحاولة المحلية في ذاكرة الصفحة فقط؛ لا JWT أو بيانات محاولة إضافية على القرص. تبديل الجلسة/unmount يلغي الطلب أو يتجاهل رده. إذا ضاعت الذاكرة قبل معرفة الحجز، تبقى القراءات والإيصالات على الخادم مرجعاً، ولا يُنشأ قرار بديل تلقائياً. العرض المقبول يعرض اتفاقه المثبت، لا مواصفات الطلب المتغيرة. لم تُعَدّ صياغة لوحة المورد أو RFQ.

## 5. العامل والحجم والتعافي

وُسّع عامل Sourcing الموجود بتوجيه صريح kind/version1 إلى معالجين مستقلين. بقيت استعادة sourcing_offer وحراسه. API وworker يستعملان العامل نفسه: دفعة25 افتراضياً/سقف100، استطلاع5 ثوان، backoff بسقف60 ثانية، حدود DB10 ثوان، وإيقاف ينتظر الجاري حتى15 ثانية. الذاكرة تنظم tick فقط؛ النية الدائمة وCAS يضمنان عدم التكرار عبر عمليات Node متعددة.

قبل الحجز، وقبل الإشعار والنشر، تُحسب BSON من المستند الخام كاملاً مع النية والإيصال والاتفاق النهائي معاً. الحد المحافظ16MiB ناقص256KiB؛ الهامش للـmetadata المحدودة وتأطير الأمر ونمو الأرقام. لا حذف تاريخ. نمو خارج المسارات المحمية بعد الحجز قد يوقف العملية بدلاً من فرض نشر غير آمن.

التعارض يبقى pending مع رمز تشغيلي آمن وbackoff حيث تسمح الهوية. لا TTL يمسح النية. الهويات/الإصدارات التالفة تحتاج مراجعة معتمدة، ولا يُفرض تغيير سعر أو ملكية. عدد المعلقات في القاعدة الأصلية **غير معلوم**؛ لم تُقرأ.

## 9. المتبقي والتراجع والتفعيل المؤجل

**أُغلق للقرارات الجديدة:** نافذة القرار النهائي بلا آثاره، تكرار القرار/الإشعار عند فقد التأكيد، سباقات S2/S3، إعادة تسعير الاتفاق من الطلب الحالي، وتسرب إيصالات التشغيل أو بيانات الاتصال عبر الاتفاق.

**بقي تاريخياً/تشغيلياً:** لا إصلاح للقرارات القديمة غير المتسقة؛ لا استنتاج لإشعاراتها من النوع أو الوقت. الأعطال المستمرة أو فساد الهوية/النسخة/السعر أو سحب صلاحية الفاعل أو نمو المستند قد تُبقي النية معلقة. يلزم رصد تشغيلي لكل operation بما فيها غير المدعومة، لا مرشح العامل السليم وحده. تزايد التاريخ ومسح الاستكمال بلا فهرس متخصص قد يؤثران على الأداء وعدالة الدفعات؛ يحتاجان قياساً وموافقة مستقلة.

لا فهرس S3 أو Migration مطلوب. فحص/تفعيل فهرس S1 في البيئة الأصلية **مؤجل ولم يُنفذ**. يلزم قبل أي تفعيل لاحق: موافقة مستقلة، نسخة استرجاع حديثة، فحص Mongo/journaling والفهرس، وتوافق جميع API/workers والعملاء، ومراقبة المعلقات. لا جاهزية تشغيل أصلية مُعلنة من اختبارات محلية.

**التراجع الآمن:** أوقف الكتابات التجارية الجديدة أولاً، وافحص المعلقات بإذن مستقل. استكمل النيات السليمة بكود S2/S3 متوافق، واحتفظ بمعالج S3 لأي نية متبقية أو أبق الكتابات معطلة إلى خطة معالجة معتمدة. لا تعِد كود قرار قديم فوق نيات معلقة، ولا تمسحها أو تحذف الإيصالات/الاتفاقات. حتى بعد التصريف، يجب إبقاء حراس وإعادة إيصالات S3 أو تعطيل الكتابات المتأثرة؛ استعادة المصدر القديم وحدها ليست rollback آمناً. لم يُنفذ أي تراجع فعلي.

**النتيجة: PASS محلياً لـS3 فقط؛ الأصلية غير مفعلة وغير متحقق منها. التوقف بعد هذا التقرير وانتظار موافقة المالك.**
