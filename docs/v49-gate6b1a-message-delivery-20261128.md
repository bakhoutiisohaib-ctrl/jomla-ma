## Implementation
- Existing authorized POST /api/rfq/:id/messages accepts optional Idempotency-Key (16–128 ASCII letters/digits/underscore/hyphen). Derive deterministic message identity from RFQ, actual actor and key; store full hash to fence collisions, compare exact normalized content and server-owned role/recipient. Atomic conditional push into the existing open thread with a pending embedded delivery receipt, journaled w:1 j:true. New keys allow intentional identical messages. Legacy clients without key retain compatibility via fresh random attempt identities; repeated legacy POSTs are not deduplicated.
- Notice uses message ID as Notification._id and an exact recipient/type/resource filter, $setOnInsert preserves readAt. Verify canonical RFQ parties before notice creation, and confirm saved receipt completed before returning 201 with submission version/phase/messageId/replayed. 503 on unconfirmed delivery (not 202, because existing clients interpret 2xx as success). Matching replay may complete after closure without appending or reopening. New messages remain subject to existing RFQ/open-thread guards and authorization. Private receipts removed from returned thread. GET thread additionally requires matching buyer/supplier identities.
- Pending receipts are discoverable via sparse nextAttemptAt index; bounded batch recovery (one due message per thread, default 25 threads, maximum 100 per scan), exponential backoff capped at 60s, ten recorded failures pause automatic recovery. Same-key explicit authorized retry still allowed. Worker start/stop wired into existing API lifecycle. Concurrent recovery can attempt the same notice but deterministic identity prevents duplicate insertions. Does not retroactively repair historical messages without receipts or notifications. Already authorized pending effects may complete after membership revocation or thread closure; subsequent unauthorized user requests rejected.
- Private no-store GET /api/rfq/:id/messages/attempt requires valid key and current party authorization. Returns rfqId, actorId and versioned submission phase absent/pending/completed with messageId when present. Read-only, no creation, no notification/read-state changes, no key/hash/content in response. Intended for upcoming UI recovery; absence is a current read, not proof of a previously in-flight request's eventual failure.
- Design grounded in MongoDB single-document atomicity and $setOnInsert semantics (https://www.mongodb.com/docs/manual/core/write-operations-atomicity/ and https://www.mongodb.com/docs/manual/reference/operator/update/setoninsert/). This is recoverable multi-document processing on standalone, not a cross-document transaction.
