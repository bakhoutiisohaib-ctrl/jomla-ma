## Contract
- Product editRevision defaults to zero; a missing historical revision is treated as zero and accepted by the atomic revision-zero filter. It is independent of view counters and general updatedAt. New keyed PUT /api/products/:id requires Idempotency-Key (16–128 ASCII letters/digits/underscore/hyphen) together with X-Product-Revision (canonical nonnegative decimal). Actor/organization, base revision and canonical accepted input fingerprint are bound to the attempt. Server fields cannot be set by body.
- Reuses existing merged-document preparation/validation, media ownership, explicit approval, pricing/availability and store constraints. Journaled conditional update (w:1,j:true) commits editable fields, next revision and bounded latest receipt in one product document. Observed moderation status/time fenced during write; moderation and view fields never overwritten. Existing public visibility remains authoritative. Same-key/same-base/same-body replay returns current saved product only if latest receipt matches; changed body or actor conflicts; stale base rejects. If a later edit already supersedes it, old receipt no longer proves the exact earlier outcome and never overwrites the later revision. Legacy unkeyed API clients retain compatibility and server-side concurrent-write fencing but cannot identify their originally opened revision or recover a lost response safely.
- Private no-store GET /api/products/:id/edit-state returns authorized current product including editRevision. GET /api/products/:id/update-attempt with original key/revision returns productId, actorId, baseRevision, currentRevision, phase absent/saved/superseded and version 1. Both enforce current manage_products permission and owner scope; lookup is read-only. No receipt, hash or key is serialized in private/public product DTOs. Public catalog fields unchanged.
- Stable visual-index job identity edit:productId:revision. Check actual compatible unique ownerId/type/idempotencyKey index before enqueueing edits. Product and job are separate writes; failure reports visualIndex unavailable, and same-key current-revision replay can repair the enqueue without incrementing editRevision. This does not automatically recover a missing job after the receipt is superseded. Job completion remains governed by existing worker; queued is not a promise of successful indexing.
- Design follows MongoDB documented conditional single-document atomic writes: https://www.mongodb.com/docs/manual/core/write-operations-atomicity/ . No replica-set migration or dependency changes.
