# المرحلة الثالثة — تشغيل النسخ والاستعادة والمراقبة

20 أكتوبر 2026. **خطة تشغيل مستقبلية، لم تُثبت أو تُجدول أو تُنفذ على استضافة.** لا تتصل هذه الوثيقة بقاعدة المشروع الأصلية. المرجع: [BACKUPS.md](BACKUPS.md)، [ملحق الأمان والتخزين](phase3-security-storage.md)، و[المخطط الرئيسي](../reports/phase3-secure-pilot-blueprint.md).

## حدود الأداة الحالية

`scripts/backup.js` يقرأ Mongo وملفات UPLOADS_DIR ويحفظ BSON وفهارس وmanifest وبصمات SHA-256 في مجلد جديد. لا يشفر ولا يرفع إلى السحابة ولا يوقف الكتابة ولا يجدول نفسه. الأدوات تقرأ backend/.env عند تشغيل CLI؛ لذلك تُستخدم مستقبلاً من إصدار staging نظيف، ببيئة staging صريحة، ودون نقل `.env` المحلي. لم تُشغل هذه الأدوات على الأصل في المرحلة الثالثة.

أداة النسخ ليست snapshot معاملات متعددة المجموعات. لضمان اتساق التجربة الصغيرة، يجب وقف **API والعامل وكل كاتب آخر** أثناء نسخ القاعدة والميديا. الحسابات والأدوار الخاصة بخادم Mongo وأسرار التشغيل والشهادة ليست ضمن تصدير بيانات التطبيق؛ توثق إعادة تهيئتها منفصلة في خزنة المالك.

## الجهات والصلاحيات

| الجزء | السياسة المقترحة |
|---|---|
| حساب التطبيق | readWrite على `jomla_pilot` فقط؛ لا صلاحية استعادة أو إدارة خادم Mongo |
| حساب تصدير النسخ | قراءة قاعدة staging والمجموعات والفهارس المطلوبة؛ اختبار الصلاحيات أولاً بحساب اصطناعي |
| حساب الاستعادة | مؤقت، مقيد بقاعدة هدف فارغة مختلفة، ومنفصل عن حساب التطبيق؛ إلغاء صلاحياته بعد التدريب |
| حساب النسخ الخارجية | bucket خاص بالتجربة، ومفاتيح مقيدة به؛ لا يعطى حساب التطبيق مفاتيح النسخ |
| سر تشفير النسخ | مستقل عن JWT، محفوظ بنسخة استعادة في خزنة المالك خارج VPS؛ لا يدخل Git أو تقارير |
| هوية إدارة المزود | ملك المالك، مع MFA ومشغل مسمى؛ لا تعتمد الاستعادة على جهاز أو شخص واحد |

## تسلسل النسخة اليومية المقترح

التوقيت الأولي المقترح 02:00 UTC يومياً، بعد اختيار نافذة لا تستخدمها الجلسات. الاحتفاظ المقترح 7 نسخ يومية و4 أسبوعية. الهدفان المقترحان RPO ≤24 ساعة وRTO ≤4 ساعات يحتاجان اعتماد المالك ثم قياساً؛ وجود جدول لا يثبت تحقيقهما.

1. تحقق من اسم المضيف واسم قاعدة **staging** ومساراتها دون طباعة URI أو السر. افحص المساحة الحرة: يجب أن تكفي التصدير الجديد والنسخة المشفرة وحيز تشغيل Mongo؛ عند عدم الكفاية لا تحذف بيانات تلقائياً.
2. حوّل مدخل التجربة إلى صفحة صيانة، ثم أوقف وحدتي API والعامل، وأي فهرسة CLI أو حساب كتابة تشغيلي. انتظر الإيقاف الهادئ وتحقق من عدم بقاء عملية كاتبة. منع POST على البروكسي وحده لا يوقف العامل.
3. أبق Mongo يعمل. نفّذ النسخ بحساب التصدير وفي مجلد جديد تحت `/var/backups/jomla-pilot/exports/` خارج الصور والإصدار والويب. تكون القراءة والكتابة في النافذة المعزولة نفسها.
4. ارفض النسخة الجزئية: يلزم exit 0 وoutcome.status=complete وmanifest كامل وبصمات سليمة. لا تدمج محتويات مجلد فاشل مع نسخة أخرى.
5. بعد اكتمال التصدير واتساقه، يمكن إعادة العامل وAPI، ثم فحص readiness وصورة ومهمة فهرسة اصطناعية. لا يلزم إبقاء التطبيق متوقفاً طوال رفع الأرشيف المكتمل إلى الخارج.
6. شفر مجلد التصدير المكتمل بـrestic ثم أرسله إلى bucket خاص خارج مزود الحوسبة، مثل B2 عبر S3-compatible API. لا ترفع BSON أو الصور مكشوفة، ولا تجعل bucket عاماً. اختيار S3 لربط restic مع B2 مطابق لتوصية [وثائق restic](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html#backblaze-b2).
7. سجل نجاح الرفع ورقم snapshot ووقت اكتماله وحجم التخزين، دون URI أو أسماء المشاركين. تحقق من قابلية قراءة النسخة عبر حساب الاستعادة المخول. النسخة المحلية وحدها ليست نسخة خارج الجهاز.
8. لا تحذف التصدير المحلي أو النسخ الأقدم إلا وفق سياسة وافق عليها المالك وبعد إثبات وصول النسخة الخارجية. لا يوجد أمر حذف أو جدولة مفعل في هذه الحزمة.

التشفير لا يمنع مهاجماً يملك مفتاح حذف repository من حذف نسخه. لا ندعي حصانة من الفدية أو عدم قابلية التغيير. يلزم إثبات احتفاظ/نسخة ثانية خارج صلاحية حساب خادم التطبيق؛ ويمكن دراسة Object Lock بعد اختبار توافقه مع صيانة restic. قرارات الاحتفاظ والإصدارات والحذف قد تغير الحجم والتكلفة، فلا تفترض 50GB سقفاً مضموناً.

## تدريب الاستعادة قبل أي بيانات بشرية

1. يبدأ بحسابات وصور وRFQ اصطناعية على staging المصرح بها، بعد إغلاق عيب عزل الصور. يسجل وقت آخر كتابة مقبولة ووقت النسخة المكتملة.
2. افترض فقد VPS أو مجلد البيانات: استخدم مضيف استعادة منفصلاً أو بيئة داخلية معزولة بلا وصول للمشاركين. لا تستعد فوق `jomla_pilot` النشطة، ولا تتصل بقاعدة المشروع الأصلية.
3. أحضر نسخة restic الخارجية، وافحص سلامتها وأصالتها من هوية المخزن وسجلاته الموثوقة؛ manifest وبصمات متطابقة وحدها لا تثبت أصالة أرشيف يستطيع مهاجم تعديله مع بصماته.
4. جهز قاعدة فارغة جديدة مثل `jomla_pilot_restore_drill_YYYYMMDD` ومجلد ميديا جديداً حقيقياً، ثم راجع `--target-db` و`--confirm-target` و`RESTORE_MONGODB_URI`. لا تطبع قيمة المتغير.
5. تستعيد الأداة المجموعات والفهارس والصور إلى الهدف الجديد فقط. تقارن الأعداد والبصمات وتقرأ outcome. عند فشل التنظيف لا تفترض عدم بقاء بيانات جزئية؛ لا تبدل مسار التطبيق إلى هدف فاشل.
6. شغل نسخة معزولة من التطبيق على الهدف **بعد المراجعة**: مورد A يرى مسودته وصورها، ومورد B لا يفتح الرابط المعروف، والمشتري يرى المنشور ويكمل RFQ. سجلات ملكية الصور المقترحة جزء لازم من النسخة بعد تنفيذها؛ الملفات وحدها لا تكفي.
7. اختبر المهمة والعامل عند الاستعادة وتحقق من حالات الحجوزات المنتهية. لا تشغل AI أو ترحل مهام من قاعدة أصلية. العامل يعيد التنفيذ عند التعافي وفق at-least-once؛ راجع الآثار ولا تفترض exactly-once.
8. سجل زمن الاستعادة الكامل حتى عودة الرحلة، وفجوة البيانات الفعلية، ونتيجة الصور والفهارس والصلاحيات. إذا تجاوز الهدف أو فشل العزل، تبقى الدعوات متوقفة ويعاد التدريب بعد الإصلاح.

| سجل التدريب المطلوب | القيمة الحالية |
|---|---|
| المضيف/إصدار البناء/نسخة Node وMongo | لم يُنفذ |
| نسخة خارجية/وقت آخر كتابة/وقت snapshot | لم يُنفذ |
| عدد المجموعات والمستندات والملفات وبصماتها | لم يُنفذ |
| نجاح تسجيل الدخول وعزل صور المسودات وRFQ | لم يُنفذ |
| مدة الاستعادة وفجوة البيانات | لم تُقاسا |
| المسؤول وقرار المرور ورابط دليل منقح | معلق |

دليل 19 أكتوبر المحلي التاريخي لا يملأ هذا الجدول: هو ليس تدريب فقد واستعادة للمضيف المقترح أو لـACL الصور الذي لم ينفذ بعد.

## مراقبة مناسبة لتجربة من عشرة مشاركين

ابدأ بسجلات systemd/Winston الحالية وبفحص دوري مسمى؛ لا يلزم شراء منصة مراقبة. لا تعرض health أو إحصاءات Mongo أو سجلات التشغيل للعامة. من يحتاج مراقبة من خارج VPS يتصل عبر VPN بهوية مشغل منفصلة؛ مراقبة من المضيف نفسه لا تكشف انقطاعه الكلي، لذلك يلزم فحص خارجي مخول.

| الإشارة | العتبة الأولية المقترحة | الإجراء والمسؤول |
|---|---|---|
| HTTPS والمدخل عبر VPN | فشل فحصين متتاليين بفاصل دقيقة | المشغل يتحقق من VPS وVPN والشهادة؛ يوقف الجلسات عند فقد الخدمة |
| الشهادة | المتبقي أقل من 21 يوماً أو فشل تجديد تجريبي | إصلاح DNS-01 وإثبات reload؛ لا تجاوز تحذير المتصفح أو فتح الموقع للعامة |
| `/health/ready` | استجابة غير 200 مرتين | فحص Mongo والقرص؛ لا تعتبر 200 فحصاً للعامل أو الصور |
| API والعامل | توقف وحدة أو 3 إعادات تشغيل خلال 15 دقيقة | مراجعة journal منقح وحادث؛ اختبار مهمة بعد التعافي |
| أخطاء 5xx | 3 أخطاء خلال 5 دقائق في الاستخدام المحدود | ربط الزمن والمسار والنسخة دون نسخ body أو أسرار؛ مراجعة قبل متابعة الجلسة |
| المهام | failed جديدة، أو pending/retry_wait أقدم من 60 ثانية للفهرسة في الحمل المتفق عليه | فحص العامل والقاعدة والقرص والملف؛ لا إعادة تشغيل جماعية عمياء |
| مهمة running | تجاوز مهلة نوع المهمة وفترة السماح لحجزها | فحص التعافي والحجز؛ عتبة مشتقة من timeout وlease وليست مدة عامة لجميع الأنواع |
| التدقيق | phase=failed أو pending أكثر من 5 دقائق | المشرف يطابق نية الإجراء مع البيانات قبل إعادة الطلب |
| القرص | تحذير 70% وحرج 85% | أوقف رفع صور جديدة عند الخطر ووسع أو نظف ملفات معروفة بمراجعة؛ لا حذف مسودات أو نسخ عشوائياً |
| الذاكرة/CPU | ذاكرة أكثر من 80% لمدة 10 دقائق أو OOM واحد | تخفيف الجلسات، فحص Sharp والتزامن وcache، ثم ترقية الموارد إن أثبت القياس الحاجة |
| النسخ | لا نسخة خارجية مكتملة خلال 26 ساعة | مسؤول النسخ يفحص الفشل؛ لا يتغير السجل إلى «ناجح» بمجرد وجود ملف محلي |
| عزل الصور | كشف واحد عابر للموردين أو رابط عام يعمل | إيقاف المدخل المتأثر فوراً، وحفظ أدلة منقحة، وإصلاح وإعادة اختبار قبل الاستئناف |

هذه عتبات مقترحة وليست تنبيهات مفعلة أو نتائج أداء. تُراجع في التدريب الاصطناعي قبل التجار. إعداد journal وlogrotate ومدة الاحتفاظ وصلاحيات الاطلاع خطوات تشغيل مستقلة؛ سجلات IP ومواضع الطلبات قد تكون بيانات شخصية، فتقتصر على المسؤولين ومدة معتمدة.

## بوابة قبول التشغيل

لا تبدأ التجربة البشرية قبل نسخة خارجية مشفرة قابلة للاستعادة، وتدريب استعادة ناجح، وفحص تعافٍ بعد إعادة التشغيل والنشر، ووصول تنبيه أو بلاغ تجريبي إلى المسؤول المسمى. لا يوجد في هذه المرحلة مزود مراقبة أو بريد أو SMS مفعل، ولا ادعاء جاهزية إنتاج.
