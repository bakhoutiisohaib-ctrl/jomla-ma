## Implementation
- Shared RfqMessageComposer replaces duplicate buyer and supplier free-message handlers, retaining the existing composer controls, labels, modal layout, and commercial actions. New recovery states use existing notice/uncertain styles; no global CSS or reference edits.
- Cryptographically random opaque attempt key scoped by account and RFQ in sessionStorage before POST. No message content, JWT or other credentials stored in attempt storage. If storage cannot be verified, no fresh send is initiated. Synchronous single-flight guard, session/unmount/request fencing and actual actor identity. No automatic send on reload.
- Fresh POST uses Idempotency-Key and requires completed versioned acknowledgement, matching thread, exact sender/role/text and unique message ID. Independent keyed GET confirms actor, RFQ, phase and exact message ID before clearing the key. Failures retain the key and freeze in-memory text. After reload the user explicitly checks status: absent allows the same attempt with re-entered text, pending retrieves the saved authorized message and enables same-key completion even after closure, completed confirms without resending. A different re-entered text is not represented as delivered if the earlier stored message differs. No new key while an unresolved key exists.
- Buyer and supplier use existing refresh paths; supplier uncertainty requires explicit conversation refresh before normal commercial actions, while status recovery stays available. Existing decision gates and modal busy controls retained.
