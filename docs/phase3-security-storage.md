# Phase 3 — خطة أمان وتخزين التجربة المغلقة

> تحديث قرار العمل في C1 بتاريخ20 أكتوبر2026: التصفح وصور المنتجات العامة المؤهلة متاحة للزائر دون حساب، بينما تظل المسودات والأصول غير المرتبطة خاصة. نُفذ ذلك محلياً عبر `/api/media` مع الفحص الحي، وفق [تقرير C1](../reports/phase-c1-public-catalog-media.md). الاختيار السابق الذي يشترط جلسة لكل صور الكتالوج لم يعد سياسة التطبيق الحالية. تبقى هذه الوثيقة وقوالبها خطة استضافة مغلقة تاريخية لم تُنشر؛ لم نغير VPN أو Caddy أو نفتح بيئة مستضافة في C1. يجب مراجعة قالب الاستضافة لاحقاً لتمرير مسار الميديا المحكوم إلى التطبيق، مع استمرار حجب `/uploads` وكل تقديم مباشر لمجلد الصور.

التاريخ: 20 أكتوبر 2026. **خطة استضافة لم تُنفذ**؛ لا نشر ولا شراء ولا تشغيل على بيانات أصلية ولا قراءة لملف الأسرار. نُفذ إصلاح الميديا لاحقاً في المرحلة A وثبت محلياً؛ راجع [تقرير الإصلاح وأدلته](../reports/phase-a-media-privacy-remediation.md). لم تثبت استضافة فعلية، ولم يعتمد المشغل فتح الدعوات. الأسعار واختيار المزود في التقرير الرئيسي.

**قرار المالك المعتمد في هذه الجولة: عزل صور المسودات لكل مورد.** هذا شرط إلزامي للتفعيل، وليس خيار مشاركة يمكن تجاوزه بموافقة تشغيلية عامة. استُبعدت وثائق الشركة الحساسة من نطاق التجربة. يفترض مخطط الاستضافة حجب /uploads حتى اكتمال إصلاح تفويض الصور واختباره؛ حجب المسار إجراء منع مؤقت وقد يمنع ظهور الصور، ولا يثبت نجاح الرحلة.

## شبكة staging المقترحة

لأول تجربة تشترط الخصوصية: خادم واحد تدخله أجهزة مشاركين معتمدة عبر VPN، مع HTTPS وعزل حسابي داخل التطبيق. يقدم Caddy الواجهة الثابتة ويمرر /api إلى API الداخلي؛ عامل systemd مستقل على الخادم نفسه. MongoDB والميديا على قرص دائم، ونسخة مشفرة خارج الخادم. يبقى React/Express/MongoDB والطابور الحالي دون تغيير أساسي. تستعمل خدمتا API والعامل حساب jomla-pilot نفسه، كي يتمكن العامل من قراءة ملفات الرفع المحفوظة بنمط0600؛ وتمنحه وحدة العامل وصول ملفات للقراءة فقط.

- المنع هو الأصل: لا منفذ عام للواجهة أو API أو MongoDB أو الصور. يسمح بمنفذ VPN المختار فقط، والإدارة من شبكة ومفاتيح مشغلين محددين. تُفحص عناوين IPv4 وIPv6 وكل منفذ أو عنوان origin قد يتجاوز البوابة.
- أصل واحد وشهادة HTTPS موثوقة على أجهزة المشاركين؛ تُوثق الشهادة وتجديدها وإعداد DNS. استعمال VPN لا يلغي شهادة المتصفح. لا تُفتح بوابة بديلة لتجديد الشهادة أو فحص الصحة دون تصميم مقيد.
- CORS_ORIGIN أصل مطابق محدد. **CORS ليس بوابة وصول**؛ لا يمنع الطلب المباشر خارج المتصفح.
- يجوز TRUST_PROXY=1 في المسار المختار ذي Caddy الموثوق الوحيد، بعد منع الوصول المباشر إلى API واختبار رؤوس IP والبروتوكول. توثق Caddy أنها تحفظ معظم الرؤوس ومنها Authorization، وتتجاهل قيم X-Forwarded-* الواردة افتراضياً لمنع التزوير. لا تضف trusted_proxies عامة أو طبقة CDN دون إعادة اختبار. [توثيق Caddy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#defaults).
- إعداد VPN على هاتف تاجر غير تقني يحتاج مساعدة قصيرة واختباراً على شبكته الفعلية. يمكن بدء جلسات قبول مشرفة بأجهزة اختبار معتمدة؛ نجاح الاتصال لدى المطور لا يثبت سهولة الاستخدام لدى التاجر.

**توافق المصادقة:** لا تضف auth_basic على API نفسه وتفترض توافقه مع JWT. الواجهة ترسل Authorization: Bearer بينما HTTP Basic يستخدم حقل Authorization أيضاً؛ قد ترفض بوابة Basic الطلب قبل التطبيق. هذا استنتاج تصميم من الكود والمواصفة، وليس فشلاً مقاساً لقالب منشور. البديل VPN، أو بوابة هوية مستقلة تستخدم cookie بعد اختبارها مع API والصور. المصادر: [Nginx Basic](https://nginx.org/en/docs/http/ngx_http_auth_basic_module.html)، [حقل Authorization في RFC9110](https://httpwg.org/specs/rfc9110.html#field.authorization).

## خصوصية الميديا

أثبت Phase 2 أن صورة الرفع تُجلب دون جلسة إذا عُرف رابطها. حفظ المنتج كمسودة يمنع ظهوره في الكتالوج فقط. يخدم /uploads كل المجلد دون فحص المالك أو حالة النشر. لا يوجد سجل MediaAsset حالي يربط كل رفع بمالكه قبل حفظ المنتج. [الاختبار](C:/Users/hp/jomla-ma/backend/tests/pilot_security.test.js:166).

**VPN لا يحل العزل بين المشاركين:** المورد B داخل الشبكة يستطيع فتح رابط صورة مسودة A إذا وصل إليه. UUID والرابط المخفي ليسا صلاحية. وضع المجلد خارج Git أو تشفير القرص لا يغير هذا السلوك عبر HTTP.

| الخيار | ما يحققه | الحد أو التغيير اللازم |
|---|---|---|
| التطبيق الحالي خلف VPN دون إصلاح الصور | يقيّد وصول أشخاص خارج الشبكة | لا يعزل صور مسودات المشاركين؛ **مرفوض للتفعيل وفق قرار المالك** |
| إتاحة صور المنتجات المنشورة فقط وحماية المسودات | يفصل الكتالوج المعتمد عن الرفع الخاص | يحتاج سجل ملكية ومسار صور يفحص المنتج والمتجر والمورد؛ فلترة كروت الواجهة وحدها غير كافية |
| كل الميديا تتطلب جلسة التطبيق، مع VPN وعزل الملكية | أفضل نطاق لأول تجربة تشترط سرية المسودات؛ المشترون يرون الكتالوج المعتمد فقط | يحتاج الإصلاح المحدود أدناه؛ إعداد الاستضافة وحده لا ينفذه |

**التوصية ضمن القرار المعتمد:** الخيار الثالث مع تفويض ملكية فعلي قبل تفعيل التجربة، واستبعاد وثائق الهوية والتوثيق من صور المنتج كلياً. يمكن متابعة الاختبارات التركيبية في بيئة معزولة؛ لا يُفعّل /uploads في القوالب ولا يُعتبر VPN إغلاقاً لعائق P1 الخاص بالمسودات.

## تصميم إصلاح الميديا — نُفذ محلياً في المرحلة A

1. عند الرفع، أنشئ سجل ملكية يتضمن معرف الأصل ومفتاح الملف وownerSupplierId وorganizationId وuploaderId والتاريخ. تستخرج الهوية من الجلسة فقط. يلزم السجل قبل وجود منتج وللملفات غير المرفقة بعد. لا تستنتج ملكية الصور القديمة من اسم أو تطابق محتوى؛ تُفصل وتراجع دون ترحيل تلقائي.
2. أوقف static المباشر لـ /uploads. قدّم الملف عبر مسار مصادق يفحص الحساب الحالي وعضوية الموظف وملكية الأصل. المالك وموظف manage_products المخول يشاهدان أصول شركتهما؛ المشتري والمورد الآخر يشاهدان فقط أصل منتج يمر فعلياً بفلتر الكتالوج المعتمد. الرفع غير المرفق خاص بشركته؛ وصول المشرف محدد ومعلن. عند إرفاق الصورة بمنتج افحص ملكية كل أصل في imageUrl وimages، لا الرئيسية فقط؛ معرفة الرابط وإقرار الحقوق لا ينقلان الملكية التقنية. لنطاق الخصوصية الصارم الأول، تقبل صور مدارة محلياً فقط؛ رابط HTTPS البعيد المتاح حالياً ليس ملفاً تتحكم المنصة في صلاحية جلبه. رفضه في API والواجهة جزء من الإصلاح المقترح، دون استيراد صور بعيدة تلقائياً أو ترحيل تخزين.
3. لا تخدم Caddy المجلد عبر file_server أو أي مسار ملفات يتجاوز فحص Express. القالب الحالي يحظر جميع /uploads و/api/media عمداً، لذلك لن تعمل الصور حتى تنفيذ الإصلاح ومراجعة التوجيه لاحقاً. يبقى العامل يقرأ الملفات محلياً؛ لا يلزم ترحيل سحابي أو جلب خارجي. تفويض Express ثم خدمة داخلية للملف بديل مستقبلي يحتاج مراجعة منفصلة، ولا يوجد في القوالب الحالية.
4. تستعمل الواجهة حالياً img مع src مباشر، فلا تمر الصورة عبر apiRequest الذي يضيف Bearer. وضع authenticate أمام static فقط سيكسر المعاينات. الحل المحدود المقترح: fetch للصورة مع Bearer إلى Blob، ثم عرض object URL وإبطاله عند تغيير الحساب أو الصورة أو إزالة المكون. لا يوضع JWT الجلسة في querystring. المراجع: [المعاينة الحالية](C:/Users/hp/jomla-ma/frontend/src/components/suppliers/ProductEditor.jsx:168)، [مصادقة API](C:/Users/hp/jomla-ma/frontend/src/api/config.js:72)، [Blob URLs وإبطالها](https://developer.mozilla.org/en-US/docs/Web/API/URL/createObjectURL_static).
5. بديل الروابط الموقعة يحتاج إصداراً مصادقاً وتفويض الأصل وعمراً قصيراً ومعالجة انتهاء الرابط. الرابط القابل للنقل يظل صلاحية لحامله حتى انتهائه؛ لا يثبت عزل B عن A عند التسريب. توضح [وثائق AWS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html) هذه الخاصية. لذلك ليس بديلاً مكافئاً لعزل جلسة التطبيق في أول إصلاح. التحول إلى cookie محمية أوسع من تعديل عرض الصور المقترح وليس شرطاً لهذه الخطة.
6. Cache-Control: private, no-store للميديا الخاصة، ودون CDN مشترك. تُفحص حالة النشر والتعطيل في الطلبات الجديدة. لا يمكن سحب صورة سبق لمستخدم مخول تنزيلها أو تصويرها؛ اختبار القبول يخص الطلبات الجديدة والتخزين المشترك.

نُفذ هذا النطاق ضمن Express وMongoDB والقرص الحالي في المرحلة A. نجحت 39 حالة خصوصية ضمن 192 اختبار خلفية، و57 اختبار واجهة، والبناء وفحص المتصفح المحلي. هذا يغلق تنفيذ الإصلاح محلياً فقط؛ تظل أدلة البيئة المستضافة واعتماد المشغل قبل الدعوة مطلوبة. التفاصيل والعقود النهائية في تقرير المرحلة A.

## قبول الخصوصية القابل للقياس

تُنفذ الحالات في staging بحسابات وصور تركيبية، مع حفظ حالة HTTP واللغة والجهاز دون أسرار:

| الحالة | النتيجة المطلوبة للخيار الموصى به |
|---|---|
| زائر خارج VPN يطلب الواجهة أو API أو صورة مباشرة | محجوب بالشبكة أو البوابة؛ لا بايتات للكتالوج أو الميديا |
| طرف داخل VPN بلا جلسة التطبيق يطلب صورة محلية | 401/403 أو404، دون بايتات الصورة |
| A يفتح رفعه الجديد قبل وجود منتج أو أي ربط، ثم مسودته | 200 ومعاينة صحيحة بالعربية والفرنسية؛ لا يحتاج الأصل وجود productId ليحصل على ملكية |
| B يطلب معرف الأصل غير المرتبط أو اسم ملفه المباشر | 403 أو404 من كلا المسارين؛ لا استثناء لصور لم تُحفظ في منتج بعد |
| B ومشترٍ يطلبان الرابط المعروف لمسودة A | 403 أو404؛ لا يعتمد الاختبار على صعوبة تخمين UUID |
| B يحاول إرفاق أصل A بمنتجه | رفض دون نقل الملكية أو نشر الأصل |
| صورة ثانوية في images أو رابط HTTPS بعيد يحاول تجاوز المسار المدار | فحص كل أصل محلي؛ رفض المصادر البعيدة في نطاق التجربة الصارم، دون جلب خارجي |
| موظف A قبل سحب صلاحية المنتجات وبعده | 200 قبل السحب؛ رفض طلب جديد بعده حتى بجلسة قديمة |
| الموظف يعيد تسجيل الدخول بعد سحب الصلاحية | جلسة جديدة لا تستعيد الوصول المسحوب؛ العضوية الحالية هي المرجع |
| جلسة A تنتهي ثم يصدر تسجيل الدخول جلسة جديدة | القديمة ترفض، والجديدة تستعيد صور A فقط؛ لا تظهر صورة سبق أن جلبها حساب آخر على الجهاز |
| مشترٍ مخول يفتح صورة منتج في الكتالوج المعتمد | 200؛ المعاينة والمقارنة وRFQ تعمل دون JWT في الرابط |
| نشر مسودة A ثم إلغاء نشرها | صورها متاحة للمشترين عند النشر فقط، ثم ترفض الطلبات الجديدة لغير المخولين بعد إلغاء النشر |
| إخفاء منتج أو تعطيل المورد أو المتجر | منع الطلبات الجديدة لغير المالك أو المشرف وفق السياسة؛ لا تسريب من cache عام |
| تسجيل خروج أو تبديل حساب أو إزالة المعاينة أثناء fetch | إلغاء الطلب المتأخر، وإزالة src الخاص بالحساب السابق، واستدعاء revokeObjectURL لكل Blob URL محرر؛ لا تظهر نتيجة متأخرة بعد تبديل الحساب |
| إعادة الطلب من cache المتصفح وproxy بعد سحب الوصول | private, no-store على المسار الخاص، وغياب نسخة في cache مشترك؛ أي طلب HTTP جديد يطبق التفويض الحالي |
| إعادة تشغيل وredeploy | الملف نفسه موجود، والعامل يفهرسه، والملكية والصلاحيات ثابتة |
| مستند شركة حساس | صفر مستندات في uploads والنسخ أو الملاحق العامة؛ إجراء خاص خارج صور المنتج |

الهدف: **نجاح جميع الحالات دون تجاوز ملكية واحد**. HTTPS ولقطة الواجهة لا يغنيان عن طلب مباشر بجلسة المورد الآخر. يعاد اختبار التفويض بعد استعادة نسخة للتأكد من استعادة الملفات وسجلات الملكية معاً.

## النسخ والاستعادة وفق الأداة الحالية

المراجع: [BACKUPS.md](C:/Users/hp/jomla-ma/docs/BACKUPS.md)، [backupDatabase](C:/Users/hp/jomla-ma/backend/services/backup.js:113). الأداة تحفظ BSON والفهارس وخيارات المجموعات والصور وmanifest وSHA-256. لا توجد فيها جدولة أو تشفير أو رفع خارج الجهاز، ولا نسخ لمستخدمي MongoDB أو الأسرار أوoplog أو إعداد replica set. checksums تكشف التلف ولا تثبت أصالة نسخة عدّلها مهاجم مع قيم التحقق.

التسلسل المقترح للتجربة الصغيرة:

1. صفحة صيانة على المدخل، ثم إيقاف وحدتي API والعامل المستقل وأي CLI كاتب. إيقاف API وحده **لا يوقف العامل المختار في هذه الخطة**. تُثبت نهاية العمليات وتوقف الكتابة. لا يوجد read-only mode جاهز؛ منع أزرار الواجهة لا يكفي. العامل المدمج بديل برمجي موجود لكنه غير مشغّل في هذا التصميم.
2. يبقى MongoDB يعمل. تستخدم أداة النسخ حساب قراءة مقيداً بقاعدة التجربة، ووجهة جديدة خارج Git وخارج uploads. تُنسخ القاعدة والميديا ضمن نافذة توقف الكتابة نفسها. القراءة local لكل مجموعة وليست snapshot عالمية أثناء التعديل.
3. لا نجاح إلا برمز خروج0 وoutcome وmanifest مكتملين. النسخ الجزئية لا تدمج ولا تعتمد للاستعادة. يعاد التطبيق بعد اكتمال النسخ وتفحص مهمة وصورة اصطناعيتان.
4. يشفّر الأرشيف خارج الأداة ويرفع إلى وجهة محمية خارج الخادم، مع احتفاظ متفق عليه ومفتاح استعادة لا يعتمد على الخادم الوحيد. حساب رفع النسخ لا يحتاج حذف كل التاريخ إذا أتاح المزود تقييد ذلك. لا يوضع مجلد النسخ على HTTP.
5. الاستعادة إلى قاعدة جديدة فارغة باسم مختلف عن المصدر وقاعدة التطبيق، ومجلد ميديا جديد. RESTORE_MONGODB_URI منفصل عبر البيئة؛ target-db وconfirm-target متطابقان. الأداة لا تستبدل قاعدة موجودة ولا تستعمل dropDatabase ولا تحول التطبيق إلى الهدف تلقائياً. حساب الاستعادة مؤقت ومقيد بالهدف؛ لا تعطى صلاحياته للتطبيق اليومي.
6. تقارن الأعداد وhashes، وتفتح صور ومنتجات وRFQ في نسخة معزولة، ويسجل الزمن والمسؤول والنتيجة. الاستعادة ليست ذرية؛ يقرأ outcome لأن تنظيف محاولة فاشلة قد لا يكتمل. ملفات صور HTTPS الخارجية لا تنسخها الأداة.

مقترح يحتاج اعتماد المالك فقط: نسخة يومية، واحتفاظ 7 نسخ يومية و4 أسبوعية، وRPO ≤24 ساعة وRTO ≤4 ساعات. لم تعتمد هذه الأهداف ولم تُقَس على استضافة. يجب أن تناسب نافذة الصيانة وحجم البيانات؛ لا تظهر كنتائج منجزة. لم تُوقف أي عملية أو تُنشأ نسخة فعلية في هذه الجولة.

## الأسرار والفحص الأولي

- حساب نظام غير root؛ حماية مجلدات الميديا والأسرار والسجلات. قواعد ومفاتيح التجربة منفصلة عن المشروع الأصلي. لا .env في build أو Git أو صورة حاوية مشتركة، ولا URI أو JWT أو رابط موقّع في تقرير عام.
- سر JWT قوي وفريد، وإجراء لتدوير الأسرار ومفاتيح VPN وإلغاء وصول المشرفين. اجتياز فحص طول السر لا يثبت سريته.
- preflight يفحص شكل الإعدادات وصلاحيات المجلد، ولا يكتب ميديا. دون check-db لا يفتح اتصال DB؛ معه يجري ping فقط. لا يثبت التخزين الدائم أو عزل الميديا أو بوابة الدخول أو صحة AI. CLI يقرأ backend/.env؛ **لم يشغّل هنا** حتى لا يقرأ الأسرار الأصلية. يستعمل لاحقاً داخل staging المعزول بإعداداته الخاصة. [الشيفرة](C:/Users/hp/jomla-ma/scripts/preflight.js:28).
- مراقبة 5xx والقرص والذاكرة والمهام pending/retry_wait/failed وأحداث التدقيق pending/failed، مع جهة اتصال للحوادث. لا تسجيل لـ Authorization أو كلمات المرور أو استجابات AI الخام.

**بوابة القرار:** تسمح هذه الوثيقة بإعداد القوالب ومتابعة الاختبارات التركيبية فقط. **عزل صور المسودات قرار معتمد، وتنفيذ تفويض الميديا واختباره عائق P1 مفتوح.** لا تفعيل للتجربة أو لمسار /uploads قبل إغلاقه، حتى مع VPN وHTTPS ونسخ مضبوطة. لم ينفذ أي إصلاح مصدر في Phase3 ولم تمنح هذه الوثيقة موافقة نشر.
